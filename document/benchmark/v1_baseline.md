## 2. 结果总览

| 场景 | 结论数字 | 第一瓶颈 |
|---|---|---|
| S1 纯 API 读 | **容量拐点 ~340 RPS**；200 用户零失败，400 用户 84% 失败 | DB 连接池 + 同步驱动线程排队 |
| S2 对局主链路 | 动作 P50 ~40ms（10 房间）；**20 房间时创建对局 30s 超时** | 每动作同步写 MySQL，写路径饱和 |
| S3 长连接广播 | **2000 连接零失败**，广播 P99 180ms 贴近 200ms 目标线 | O(N) 顺序广播（见曲线图） |
| S4 突发流量 | 10 倍突发失败率 10%，P90 恶化至 7.8s，**回落后需恢复期** | 无排队/降级机制，突发直接打穿 |
| S5 热点场景 | 500 混合用户 11.5 万请求零失败，P99 160ms | 稳态可扛，短板在突发不在稳态 |

## 3. S1 纯 API 读接口

命令：`locust -f ../bench/locustfile.py --headless -u {N} -r {N/5} -t 60s --host http://localhost:8000`

| 并发用户 | 总请求 | 失败 | 实测 RPS | P50 | P95 | P99 |
|---|---|---|---|---|---|---|
| 30（冒烟） | 6,270 | 0 | 210 | 9ms | 28ms | 43ms |
| 100 | 19,820 | 0 | 330 | 170ms | 310ms | 470ms |
| 200 | 20,464 | 0 | 341 | 520ms | 650ms | 690ms |
| 400 | 1,494 | 1,256 (84%) | 崩溃 | 7,800ms | — | — |

**分析**：30→200 用户 RPS 从 210 涨到 341 即触顶，延迟以排队方式劣化（P50 从 9ms 涨到 520ms 而零失败）；400 用户直接打穿。瓶颈指向 PyMySQL 同步驱动 + 线程池 + 默认连接池（15）的排队模型——每个请求在 DB 上花费的墙钟时间决定了并发上限。

## 4. S2 对局主链路

命令：`locust -f ../bench/locust_s2.py --headless -u {N} -r {N} -t 120s --host http://localhost:8000`
（每个虚拟用户驱动一个完整对局；表中动作延迟仅含真人动作，AI 动作走 Celery 内部回写）

| 并发房间 | 真人动作数 | 动作 P50 | 动作 P99 | 快照轮询 P50 | 备注 |
|---|---|---|---|---|---|
| 5 | 368 | 36~42ms | 130~270ms | 6ms | 全部成功 |
| 10 | 359 | 42~50ms | 140~300ms | 6ms | 全部成功 |
| 20 | 165 | 44~75ms | 66~190ms | 15ms | **创建对局 avg 35.8s、5 次 30s 超时** |

**分析**：10 房间内动作延迟稳定；20 房间时**创建对局路径先崩**——创建触发 MySQL 写入 + 8 个 AI 任务同时回写，每动作同步落库（`game_events` insert）+ 连接池 15，写路径饱和。这正是 D 组"热路径重构（Actor + Write-Behind）"的直接证据：当前架构的容量天花板由"每动作一次同步 DB 写"决定。另有少量 mission 动作失败（5~7 次/千），属 DEVLOG 005 竞态家族。

## 5. S3 长连接与广播

命令：广播源 `--rate 5` + `locust -f ../bench/locust_s3.py --headless -u {N} -r {N/10} -t 45s --host ws://localhost:8000`

| 单房间连接数 | 连接失败 | 握手 avg | 广播 P50 | 广播 P99 | 广播 max |
|---|---|---|---|---|---|
| 100 | 0 | ~30ms | 6ms | 12ms | 27ms |
| 500 | 0 | 167ms | 22ms | 46ms | 69ms |
| 1000 | 0 | 233ms | 46ms | 91ms | 130ms |
| 2000 | 0 | 390ms | 84ms | 180ms | 326ms |

![广播延迟劣化曲线](images/s3_broadcast_latency.png)

**分析**：连接建立零失败到 2000（修复 DEVLOG 006 后）；广播延迟随连接数**近线性劣化**（每 10 倍连接 ≈ 8 倍延迟）——`manager.broadcast` 的 O(N) 顺序 send_text 是明确瓶颈，2000 连接时 P99 180ms 已贴近 200ms 目标线。E 组（事件合并帧/分级推送/网关分离）的靶子。

## 6. S4 突发流量

命令：`locust -f ../bench/locust_s4.py --headless --host http://localhost:8000`（阶梯形态：50 用户 60s → 500 用户 60s → 50 用户 60s）

| 阶段 | 表现 |
|---|---|
| 基线（50 用户） | 正常，P50 ~18ms |
| 10 倍突发（500 用户） | 失败率 10.09%，P90 恶化至 7.8s（排队特征） |
| 回落后 | **需要恢复期**——突发结束后立刻跑 S5 曾出现 70% 失败，间隔后恢复 |

**分析**：当前系统对突发无任何缓冲——无限流排队、无降级，请求在 DB/线程池排队直到超时。H 组（限流/降级矩阵/熔断）的验收场景。"恢复期"作为韧性指标纳入后续复测。

## 7. S5 热点场景

命令：`S3_GAME_ID=s5-hot-room locust -f ../bench/locust_s5.py --headless -u 500 -r 50 -t 60s --host http://localhost:8000`（400 WS 旁观 + 100 热榜读者）

| 指标 | 值 |
|---|---|
| 总请求 | 115,205（60s） |
| 失败 | 0 |
| 聚合 P50 / P99 | 29ms / 160ms |

**分析**：稳态热点（单房间广播 + 热榜集中读）当前架构可扛；热榜接口有 Redis 缓存兜底（P50 70ms 内）。注意这是在 DEVLOG 006 修复之后——修复前 16 条 WS 连接即雪崩。

## 8. 瓶颈定位与 v2 优化主线映射

| 优先级 | 瓶颈 | 证据 | v2 主线 |
|---|---|---|---|
| P0 | 每动作同步写 MySQL | S2：20 房间创建路径 30s 超时 | D 组 Actor + Write-Behind |
| P1 | O(N) 顺序广播 | S3：延迟近线性劣化，2000 连接触目标线 | E 组合并帧/分级推送/网关分离 |
| P2 | 突发无缓冲 | S4：10 倍突发 10% 失败 + 恢复期 | H 组降级矩阵 |
| P3 | DB 连接池/线程池排队 | S1：340 RPS 拐点 | D/F 组（连接池调优 + 缓存卸载） |
