## E. 长连接与广播（简历⑤）

> 简历⑤点名了五个机制：独立网关、Redis 路由表跨节点扇出、同 Tick 合并帧、分级推送、慢消费者背压。**这五个都得真做出来**——2,000 连接和 180ms 已经有实测，但那是优化前的数，不能拿来给这些机制背书。

### E.1 WS 网关独立服务
- [ ] 网关服务拆分：连接维持、握手鉴权、消息转发，不含业务逻辑
- [ ] 连接 → 网关节点映射存 Redis（简历里的"Redis 路由表"就是这个）
- [ ] 跨节点扇出：逻辑层广播经 Redis Pub/Sub 分发到目标网关

### E.2 广播优化
- [ ] 事件合并：同房间同 Tick 多事件合并为一帧
- [ ] 分级推送：操作者单播 / 房间即时广播 / 旁观者聚合批量
- [ ] 慢消费者背压：写缓冲超阈值主动断开，保护节点

### E.3 验证
- [ ] S3 复测：拆分后 2,000 连接**不劣化**，广播 P99 仍 ≤ 200ms（这是"拆分不掉性能"的证明，不是冲更高连接数）
- [ ] 3 节点扇出验证：房间成员分布在不同网关，广播全部送达且延迟不劣化
- [ ] 慢消费者隔离演练：灌一个不读的连接，验证它被断开而其他连接无感
- [ ] 若要冲更高连接数：先把 `somaxconn`（当前 128）调高、验证 locust 单客户端 IP 容量（约 15k），否则测的是压测端瓶颈
- [ ] ADR-03（广播合并与分级推送）——可用 DEVLOG 替代
