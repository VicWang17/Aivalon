## F. 缓存（简历⑥·上）

- [x] L1 进程内 + L2 Redis 两级缓存,未命中回源 MySQL：`core/cache.py`,加在**回放事件流**读路径（全站唯一真回源 MySQL 的接口,且事件只增不改）。**刻意不加在对局状态路径**——那里的 `games` 是 Actor 权威状态,非归属节点留副本会重现 DEVLOG 018 对局回退。L1 有条数上限 + TTL 即一致性上限,指标 `cache_reads{level}`（DEVLOG 025）
- [x] 事件驱动失效 + TTL 兜底：Pub/Sub 失效通道补上 L1 跨进程失效不了的洞（L2 共享删一次即可,L1 在各进程堆里得喊一声）。**失效点挂在 flusher 刷库成功之后**,不在动作发生时——事件走 Write-Behind,提前失效会让读回源到还没刷入的 MySQL、把旧结果重新缓存 300s。失效失败不上抛,L1 短 TTL 才是保证（DEVLOG 026）
- [x] 穿透：布隆过滤器拦截不存在的 game_id：`core/bloom.py`，md5 双哈希（内置 `hash()` 受 `PYTHONHASHSEED` 影响，跨进程算出不同位 → 共享位图失效，同 C05）。**能当门卫全靠误判单向**：只会误判"存在"，绝不误判"不存在"。三条工程约定维持"无假阴性"：空位图放行 / key 不设 TTL / 启动时位图不存在则灌一遍库里已有 id——少一条就会把真实房间 404 掉。拦截点放在**跨节点转发之前**（省掉一次往返），刻意不拦 `load_game`（AI 任务与快照恢复走它）。Redis 故障一律放行，指标 `bloom_rejects`（DEVLOG 027）
- [x] 击穿：singleflight 互斥回源：`cache.py` 的 `_load_once`，`_inflight` 存 `key → future`。**用 future 不用锁**：锁只保证不同时查，后来者拿到锁还会各自再查一次；future 直接把第一次的结果交给所有等待者，N 个并发 → 1 次查询。两个真坑：① `asyncio.shield` 挡取消传播——不加的话一个等待者被取消会连带打断回源方和其他等待者，**收敛故障的机制反而放大故障**；回源方被取消则必须放掉等待者，所以捕获 `BaseException` 而非 `Exception`（`CancelledError` 不是 `Exception` 子类）。② 占位前必须二次检查 L1——L2 读那次 `await` 期间别的任务足够跑完一次回源并回填。互斥按 key 不按全局。边界：**进程内互斥不是集群级**，M 个进程最坏 M 次回源；不上分布式锁是因为它要在每次未命中路径上多付一次往返，而把 N 压到 1 是数量级改善、把 M 压到 1 只是常数级。10 项单测，`gather` 50 并发断言只回源 1 次，不用压测（DEVLOG 029）
- [x] 雪崩：逻辑过期异步重建 + TTL 抖动：L2 存的是信封 `{"v": 值, "exp": 逻辑过期时刻}`，物理 TTL = 逻辑过期 + 60s 宽限窗口 + ±10% 抖动。读到逻辑过期的值**先返回旧值、重建放后台**，调用方一次也不等（singleflight 把 N 次回源压成 1 次，但那 1 次还是有人在等）。抖动治的是**雪崩会自我强化**——第一轮集体到期后幸存的 key 全被对齐到同一时刻，下一轮更整齐。两个坑：① F-4 那个二次检查 L1 会让重建空转（旧值刚被填进 L1），所以重建走 `skip_l1` 但照旧查 `_inflight`；② `_decode` 返回三元组而非二元组——**None 是合法缓存值**，拿它当解析失败会把 F-3 的空结果缓存废掉。`KEY_PREFIX` 升 v2（值结构变了必须换前缀，这是 F-1 留它的用处）。13 项单测，核心那条判耗时不判返回值（DEVLOG 030）

## G. 热榜（简历⑥·下）

- [x] 写路径：对局结束 → MQ（已有 Celery `stats_queue`）→ 批量合并 ZINCRBY：`core/rank_buffer.py`，增量先 `HINCRBY` 攒进 HASH（field = `榜|玩家`），后台循环每秒 `RENAME` 换出 + pipeline 批量 `ZINCRBY`。**`ZADD` → `ZINCRBY` 省掉的不是一条命令而是那次查库**：`ZADD` 写绝对值就必须先知道现在是多少（那次 MySQL 查询的来源），`ZINCRBY` 写增量而增量在对局结束那刻已经知道。代价是不幂等，接受 at-least-once——榜是可以从 MySQL 全量重建的派生数据。收益分两笔别混着吹：**批量化是主要收益**（N 次往返变 1 次），同 member 合并在本项目里不大（一个人没法同时结束两局），比值看 `rank_updates_buffered / rank_updates_applied`。三个坑：① 换出必须 `RENAME` 不能"`HGETALL` 后 `DEL`"，后者会把两步之间进来的写连带抹掉且无从发现；② `RENAME` 的原子性顺带做掉多节点互斥，不用再套分布式锁；③ 删除放在 `ZINCRBY` 之后（宕机则重放一次，可自愈），反过来是永久少算。顺手修了既有 bug：`stats.py` 拿大写名字的集合比小写枚举值，`is_evil` 永远 False——坏人赢了不加分、好人赢了全场都加分，**不报错只是全算错**；判据收敛到 `game_enums.camp_of()`。13 项单测（DEVLOG 031）
- [x] 读路径：分片 ZSET + 定时归并 Top N + L1 本地缓存：每榜拆 8 片（`rank_buffer.shard_of`，md5 不用内置 `hash()`——写入进程和归并进程不是同一个，同 C05 盐坑），归并循环每 5s 取各片 Top N 排序、**连展示字段一起烤进快照 key**，读接口只读快照。**按 member 哈希分片而不是按写入轮转**：一个人的分数完整待在一片里，所以全局 Top N ⊆ 各片 Top N 的并集，归并只读 `SHARDS × limit`（8×10=80）行、**上界与总人数无关**；轮转分片会把同一个人拆散在多片，必须全表扫才能排序——**分片键约束的是查询形态**。不用 `ZUNIONSTORE`（要并全部成员，开销随人数走且堵住单线程 Redis），改在应用侧排序。原来"查 Redis 排序 → 拿 id 回 MySQL 查用户名场次"等于**榜单 QPS 直接压在库上**，现在读路径一次都不查库，查库降为每 5s 最多一次（口径 `rank_reads{result}`：`merged` 跟着读 QPS 涨就说明归并循环没跑）。快照**按最大 limit 存一份**、切片在应用侧（`limit` 是无界维度，按它分别存就是让 key 跟请求参数爆开，同 C02）。`get_or_load` 传 `redis=None` 只复用 L1 + singleflight（快照本身就是 L2）。归并循环**刻意不互斥**（纯读+覆盖写，重复只费 CPU），和写路径 `RENAME` 必须互斥恰好相反——**看重复执行会不会改变结果，不看是不是"后台任务"**。16 项单测（DEVLOG 032）

## H. 韧性（简历⑦）

- [x] **AI 降级开关运行时可切**（L1/L2 的前置）：`core/switches.py`,开关值存 Redis(`switch:ai_use_llm`),各进程读同一个 key、本地带 1s TTL 缓存,操作入口 `/internal/switches`（GET/POST/DELETE,`X-Internal-Secret` 鉴权,不进 OpenAPI）。原来 `AI_USE_LLM` 启动时读一次,要改就得重启所有 Celery worker,而 AI 决策就跑在 worker 里——**需要重启才能生效的降级开关在事故里等于没有**。两个 TTL 方向相反：**开关本身不设 TTL**（降级是人做的决定,不能自己弹回来,半夜降完睡觉 TTL 一到故障重来一遍),**本地缓存必须设 TTL**（开关每个 AI 回合读一次,不然就是把 Redis 挂在热路径上;TTL 即一致性上限)。**失败方向：Redis 读失败优先保持本进程上次读到的值,哪怕已过期**,只有从没读到过才退回配置默认值——切降级往往正因为线上在着火,而 Redis 抖动本身就是着火的一部分,退回默认值等于开关在最需要它的时刻自己失效;这和缓存"读不到就放行回源"恰好相反,**一个是"可以慢"另一个是"不能变"**。默认值仍取自 `settings.AI_USE_LLM`,压测那套环境变量照旧有效。开关状态上指标 `aivalon_degrade_switch{name}`（降级动作不可观测就是静默变更)。11 项单测（DEVLOG 033）
- [x] **LLM 舱壁**：`asyncio.wait_for` 包住整次调用 + `max_retries=0`,超时/异常一律返回 `{"error": ...}` 回落规则引擎。原来把 `timeout` 直接传给 OpenAI SDK,看着像"最多等 45 秒"——实际 SDK 的 `timeout` 是**单次尝试**的、默认还重试 2 次、重试间有退避,真实上界 140 秒以上。**"我传了 timeout"和"这次调用有上界"是两回事**,上界要卡在自己代码里、不能外包给依赖库的参数（`wait_for` 在最外层,SDK 换版本这个上界还成立）。**有规则引擎兜底时重试的价值是负的**——它花掉的是玩家的等待时间,所以关掉 SDK 重试。**超时绝不上抛**：抛出去走 Celery 重试,而重试打的还是那个慢掉的 LLM,一次慢放大成五次慢。`asyncio.TimeoutError` 分支必须排在 `except Exception` 前面（3.11 起它就是内置 `TimeoutError`,而那是 `OSError` 子类,会被 `except Exception` 抓走;写反不报错、只是超时全记进 error 档,**指标静默失真**）。顺手接上了 `llm_calls_total` / `llm_latency`——它们声明在 `metrics.py` 但全代码库从没 `inc()` 过。指标口径两条：**失败和超时的耗时也要记**（只记成功的话 LLM 全超时时曲线反而变好看,最该告警的时刻一片绿),**四档分开**`success`/`timeout`（依赖慢了→降级扩容)/`invalid`（依赖坏了,通了但非 JSON→改 prompt)/`error`（鉴权配额网络)。超时值提到配置 `AI_LLM_TIMEOUT_SPEECH=45` / `AI_LLM_TIMEOUT_ACTION=20`,事故里可压小。11 项单测（DEVLOG 034）
- 分层限流（三层，分开做）：
  - [x] **网关层准入：全局令牌桶 + IP 令牌桶**。`core/admission.py` + `AdmissionMiddleware`,挂最外层,被拒的请求不碰任何后端资源。和已有 `rate_limit.py`（按 user_id 的业务规则）是两层不同的东西——**一万个用户每人只建 1 局完全合规,机器照样倒**,按用户限流保护不了系统容量。不复用固定窗口的两个理由：窗口边界能挤进 **2 倍**流量;更关键是固定窗口只有"N 次/秒"一个旋钮,**表达不了"允许突发到 400、稳态只给 200/s"**,而这正是真实流量的形状。令牌桶把它拆成两个独立旋钮：`capacity`=突发上限,`rate`=稳态速率。**必须用 Lua**：「读桶→算补令牌→判断→写回」是读改写序列,多进程共享一个桶,`GET`+`SET` 会让两个进程同时读到"还剩 1 个"各自放行。**时间基准取 `redis.call('TIME')` 不取节点本地时钟**——节点间时钟偏差会直接变成令牌数偏差,快的那台等于给自己多发配额（**共享状态的时间基准也是共享状态**,同 C05）。**失败方向：Redis 读失败一律放行**,限流器是保护机制不是可用性依赖,抖一下就拒全站的话它自己成了新单点、造成的故障比防的还大——这和 H-1 开关"读不到保持降级态"**恰好相反**。三处"限流器自己变成放大器"的坑：`/health`+`/metrics` 必须豁免（拒了健康检查→LB 摘节点→剩下的更快被拒→**限流器亲手把过载放大成雪崩**）、429 必须带 `Retry-After`（不说等多久客户端就立刻重试,重试本身变成新峰值）、**被 IP 层拒掉的不能扣全局桶**（否则刷接口的 IP 顺带烧掉别人配额,而那正是它想干的）。**不读 `X-Forwarded-For`**（可伪造的限流键等于没有限流键）。中间件顺序刻意让 TraceId 包在外层,429 也要有 trace_id 和访问日志。桶 TTL 按 `cap/rate`（恰好攒满)设,无损——**过期消失的桶和满桶完全等价**,顺手解决 IP 桶随访客数无限增长。指标 `aivalon_admission_rejects_total{layer}`,global/ip 分开（**看到它们要做的事不同**：global=系统到顶该扩容,ip=某来源在打我该封）。阈值暂拍（全局 400/200,单 IP 60/20),等 S4 出真实拐点再定。12 项单测（DEVLOG 035）
  - [x] **应用层：固定窗口换滑动窗口 + 补齐遗漏路由**。新写 `core/sliding_window.py`（ZSET 滑动窗口日志),**所有**限流器统一到它上面,`rate_limit.py` 退化成配置入口（各接口 scope 与阈值)——刻意统一不并存,**留两套限流机制比留任何一套都糟**,读代码得先判断这条路由走的是哪套才知道边界行为。换算法的理由：`fastapi-limiter` 的 Lua 是 `SET px`+`INCR` 即**固定窗口**,key 从第一个请求起算过期、到点整批清零,于是**上小时最后一秒建 10 局 + 下小时第一秒再建 10 局 = 2 秒内 20 局**,而每次都"没超过 10 局/小时"——**业务承诺被算法实现细节打了个对折**。顺手修掉一个真漏洞：`default_identifier` **读 `X-Forwarded-For`**（客户端可随便填),而 `send-code`/`login` 原来没传 identifier 用的正是它——**最需要限流的两个接口限流键可以伪造**,换个假 IP 就能无限发验证码（每封花真钱)、无限撞库。覆盖面也补齐：原来只有建局+提交动作两个路由,现在加上 register、榜单、回放、历史、对局快照,并按"这个操作多贵"和"真人能多快"分档（发码 3/小时、登录 10/5 分钟、注册 5/小时、读接口 60/分)——**不是所有接口配一个数**。两层用不同算法是因为要的性质不同：网关层要突发与稳态分开调（令牌桶两个旋钮),应用层要**没有可利用的边界**（承载业务承诺)。滑动窗口代价是内存 O(窗口内请求数),但**先 trim 再计数、超了不写**,所以 ZSET 上界就是 `times` 本身;这也划定适用范围——`times` 小时划算,`times` 很大（网关 200/s)就该用令牌桶（**只存 2 个数字,与流量无关**)。三个易错细节：**trim 必须在计数前**（先计数会把已滑出的算进来,且不 trim 则 ZSET 无限长大)、**超限时刻意不写入**（写了则每次被拒都把窗口往后推,**重试的客户端把自己永久锁死**)、**member 用 uuid 不用时间戳**（member 相同会被 ZSET 覆盖成一条,**并发越高漏计越多**,限流器恰在压力最大时失效);score 才是跨进程比较基准,取 `redis.call('TIME')`。指标 `aivalon_rate_limit_rejects_total{scope}`（scope 低基数可进 label,user_id 绝不能进,C02)。15 项单测（DEVLOG 036）
  - [x] **资源层·上：单房间事件风暴保护**。`room_actor.py` 上加两条上界——队列满抛 `RoomOverloaded`（路由层转 503 + `Retry-After`）、等待超时抛 `RoomActionTimeout`（转 504）。前两层统计不到这一类：**8 个人对着同一局猛点，每个人都没超自己的 1 次/秒，那个房间的队列却能排到几千个**，而队尾的人要等前面全部跑完——按用户按 IP 都看不见，只有**持有资源的地方**看得见。**先判满再入队，刻意不用有界 Queue 的 `await put`**：那是让提交方排在队列外面等，队伍只是从看得见的地方挪到看不见的地方，延迟照样无上限;过载时最不该做的就是让调用方多等，**等待本身就是资源**。最要紧的一条：**超时后还没出队的动作必须丢弃**（`wait_for` 取消 future 恰好提供了"提交方还在不在"这个信号，所以别换成 `shield`），否则客户端按超时重试一次、服务端把排队那次也跑了，**一个动作生效两遍**，投票提名重复执行会直接把对局算错;这也是队列上界的另一半价值——**过载时队里堆的多半都是已经没人等的动作**。两种拒绝**刻意分开不合并**：`queue_full` 压根没入队所以**一定没生效**可安全重试（503），`timeout` **可能已经在跑、服务端无法断言**（504，客户端该先拉状态再决定）——**错误码要如实反映"这次到底做没做"**。顺手结清两条已知欠账：空闲判定与新动作入队撞车（`wait_for` 取消了 `get()` 后 `put_nowait` 进来的动作没人取、future 永不完成，原来是永久挂起）、注销必须**比对身份不能按 game_id 盲删**（老 Actor 退出回调晚于新 Actor 建好会删掉正在用的那个，同一房间短暂两个写者，**单写者模型就破了**）。指标 `aivalon_room_overload_total{reason}`（game_id 绝不进 label，C02）。11 项单测（DEVLOG 037）
  - [x] **资源层·下：AI 队列深度上限 → 自动降级**。`core/ai_queue.py`：投递侧 `enter()` 登记"在飞任务"、token 随 Celery 任务带下去，worker 跑完注销；worker 执行前读一次深度，超阈值就 `get_action(force_fallback=True)` 摘掉 LLM 走规则引擎。**这一层过载时不能拒**——前面三层（拒 HTTP / 拒建局 / 拒动作）都有个共同前提：**对面有客户端、它会拿到错误码会重试**；AI 回合没有这个前提，被丢掉就没有任何人会再提交它，**房间不是变慢而是永久卡死**。所以"限流的手段是拒绝，但过载控制的目的不是拒绝"，判据很具体：**对面有没有一个会重试的客户端**。**降级降的是"每个任务多贵"不是"放几个进来"**：同样长的队列，走 LLM 每条十几秒、走规则引擎每条毫秒级——**队列长度一点没变，排空时间差三个数量级**,而且对玩家的可见损失最小（对局照常，只是 AI 说话变套路）；这就是 5 级矩阵的 L2，只不过按深度自动触发。**记账在投递侧**（等 worker 领到才记的话，积压期间躺在队列里的一个都不算，深度永远看着很小），**判断在 worker 里**（投递到执行隔着排队，用投递那刻的深度等于拿几十秒前的旧情况做现在的决定）。**刻意不问 broker 要 message_count**：那是一次阻塞 AMQP 往返，加在每个 AI 回合上就是把 broker 挂进热路径——**保护机制自己成了新的延迟来源**。**关键选型：ZSET 存"在飞任务 → 投递时刻" + 租约清理，不用 INCR/DECR**——worker 被 kill -9 不会注销，纯计数器**误差只会单向累积**，攒够阈值后系统**永久停在降级态**且从曲线上分不清是漏账还是真积压;**凡是"登记后靠对方注销"的计数都必须假设对方不会来**（同 C06）。租约有下界（必须 > LLM 舱壁 45s，取 120s）：小了会把**正在跑的**任务当漏账清掉，深度永远上不去、**降级永不触发且不报错**——测试钉的是这个关系不是具体数值。**失败方向：读不到深度报 0 = 不降级**（自动推断出来的降级，推断不出来就别擅自降；误降是全站说套话，不降有 H-2 舱壁兜着——**哪边代价可恢复就往哪边倒**）。这是本项目**第四种失败方向，四种全不一样**：缓存放行回源 / 开关保持现状 / 限流器放行 / 自动降级不降。**自动降级与人手开关刻意两个入口**（`force_fallback` vs `switches`）：一个每回合重判、一个要留到人来撤销，**生命周期不同的东西不能共用一个状态位**,混一起就是"人的决定被机器覆盖"或"机器的决定撤不回去"。重试中的任务不注销（重试的任务恰恰是积压的一部分）；任务签名加参数**必须给默认值**（队列里躺着上一版投递的消息,少一个参数就是一批 TypeError 进死信队列）。顺手接上从没 `set()` 过的 `ai_queue_depth`,新增 `aivalon_ai_turns_degraded_total{reason}`（**自动降级尤其必须可观测：没人按过按钮**）。16 项单测（DEVLOG 038）
- [x] **5 级降级矩阵 + 一键开关中心**：`core/degrade.py`,档位存 Redis(`degrade:level`)、本地 1s TTL 缓存,入口 `/internal/degrade`（GET 带整张矩阵 / POST 拧档 / DELETE 一键回 0,`X-Internal-Secret`,不进 OpenAPI）。L1 只砍 AI 发言 / L2 AI 全决策走规则引擎 / L3 冷路径降频 / L4 建局排队 / L5 拒新开局。**刻意是一个整数旋钮不是 5 个复选框**：5 个复选框要求操作的人在压力下自己记住依赖顺序（先关发言还是先关热榜?关了 L4 要不要顺手关 L2?),而矩阵的本质是**这些措施有序且累积**——用一个数字表达是精确的,用 5 个布尔则允许"L3 开着但 L1 关着"这种没意义的组合。**最容易写错的一条：判定必须 `>=` 不能 `==`**——`if level == 2` 在升到 3 档时会把 LLM 自己开回来,**往更严重的方向拧,反而恢复了更贵的功能**。**档位排序依据是"这一刀砍多少成本"除以"玩家多疼"**：AI 发言排第一（最贵的一次 LLM 调用,输出长温度高超时上界 45s 是投票两倍多,且说什么都不改变胜负）,"不让人进来玩"排最后;排错顺序就是降了一级没省到成本、只好继续往上拧。**L3 是降频不是关掉**（榜单晚十几秒没人投诉,**查不到榜单会被当成故障**),所以 `cold_path_interval()` 返回间隔而非布尔,热榜归并与回放两级 TTL 都乘倍数——TTL 即一致性上限,花掉的是"数据可以多旧";归并循环里**每轮重读档位**,循环外读一次就等于要重启才生效（同 H-1）。**L4 的配额刻意是全局的不是按用户的**：按用户那个（10 局/小时）一直在生效但保护不了系统容量（一万人每人 1 局全合规,机器照样倒,同 H-3a),L4 压的是"全站每秒开几局",复用 H-3b 滑动窗口。**L4/L5 的差别不只是数字大小,是给客户端的语义不同**：L4 = 429 + `Retry-After`（等等能建,该排队重试),L5 = 503（这功能整个关了）;L4 配额**必须是正数**,配 0 就等于 L5、这一级白设。**L5 的闸只挂建局不挂对局内动作**——"只服务进行中的房间"全部含义就在这里,**挡错地方就不是降级而是故障**,用 AST 断言钉住调用点。**越界报错刻意不夹逼**（手滑输入 50 夹成 5 就是静默把全站新开局拒了,**夹逼是替用户猜意图而这里猜错的代价是全站不可用**）。**"读不到"与"读到脏值"失败方向相反**：前者保持上次档位（人做的决定,同 H-1),后者按 0 档（宁可不降也别因一个坏值把全站拒了）。AI 侧四条通路取"或"（`force_fallback` / 人手开关 / L2 / L1）——**谁都不该被别人的"不用降"覆盖掉**,但 reason 分开上报（要人做的事不同）。**降级拒绝与限流拒绝分开计数**：同一个 429 背后是"有人打得太猛"和"我们自己关的闸"两件事。**恢复必须和降级一样一步到位**（要求逐级退就是要求人在最累时多做 5 次操作),下调多级只打 warning、不在代码里强制逐级。指标 `aivalon_degrade_level`（一个 Gauge 不是每级一个,档位累积、要的是"何时拧到几档"这一条线）+ `aivalon_degrade_rejects_total{reason}`。24 项单测（DEVLOG 039）
