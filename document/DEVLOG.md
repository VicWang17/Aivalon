## 概念速查（面试向 · 随时补充）

> 非踩坑类：开发中遇到"不懂但必须懂"的概念，用问答式笔记沉淀在此，每条标注关联代码/配置位置。

### C01 Prometheus 是什么（2026-08-10 · A 组）

- **一句话**：专门存"监控数字"的时序数据库 + 采集器，大厂监控体系事实标准
- **核心模式是 pull**：它不是等你上报，而是每隔 15s 主动访问 `/metrics` 把当前所有数字抓走存起来（对比：MySQL 是你往里写）
- **数据结构叫时间序列**：指标名 + 一组 label = 一条随时间变化的曲线。例：`http_requests_total{handler="/health", method="GET", status="2xx"}` 就是"该接口 GET 2xx 的累计请求数"这条曲线。有了曲线就能算增速 = QPS
- **分工**：Prometheus 存数据和告警，Grafana 负责画图（Grafana 只读不存）
- **关联代码**：`backend/app/main.py` 的 `Instrumentator().expose(app)` 就是被拉的 `/metrics`

### C02 label 基数爆炸（2026-08-10 · A 组）

- **label**：指标上的维度标签，如 `{handler="/health", method="GET"}`
- **基数 = 取值个数**；**每种 label 取值组合 = 一条独立时间序列**，都要占内存
- **爆炸机制**：label 放低基数维度（路由十几个 × 方法几种 ≈ 几十条序列）没问题；放 `game_id`/`user_id` 这种高基数值，一万个房间 = 每个指标爆炸成上万条序列，Prometheus 内存打爆、查询卡死。这是 Prometheus 最经典的生产事故
- **正确分工（面试标准答案）**：metrics 看聚合趋势，日志查个案（带 trace_id/game_id），trace 看调用链——"metrics 看趋势、日志查个案、trace 看链路"
- **关联代码**：`backend/app/core/metrics.py` 头部注释；label 只用了 event_type / action_type 这类低基数维度

### C03 Histogram、桶与"P99 是估算"（2026-08-10 · A 组）

- **问题**：想算 P99 延迟，但 Prometheus 每 15s 才拉一次，拿不到每个请求的原始值，无法排序
- **Histogram 的解法**：不存原始值，只存"落在每个区间的累计个数"。区间边界就是桶（buckets）。一个延迟 37ms 的观测，会给 ≤50ms、≤100ms、≤1s……所有不小于它的桶各 +1
- **P99 怎么算出来**：总 1000 个请求，第 990 名落在哪个桶？查各桶计数找到它落在 50ms~100ms 桶，然后**假设桶内均匀分布做线性插值**，估出约 98ms——所以 P99 是估算值不是精确值
- **推论（面试追问点）**：估算精度取决于桶边界设计。桶要按"目标延迟"加密设置——我们要验证 P99 < 100ms，就在 5ms~200ms 区间密集设桶（见 `metrics.py` 的 buckets 参数）；桶设糙了 P99 就没意义
- **关联代码**：`backend/app/core/metrics.py` 的 `ws_broadcast_latency` / `game_action_latency`

### C04 Locust 是什么（2026-08-10 · B 组）

- **一句话**：用 Python 代码定义"虚拟用户行为"的压测工具——你写用户会做什么，它模拟成千上万个这样的用户并发打你的系统
- **压测工具三要素**：制造并发（N 个虚拟用户）、定义行为（节奏/接口/数据）、统计结果（QPS/分位数/错误率）
- **Locust 的差异化**：行为用 Python 类表达，`@task(权重)` 声明任务比例，`wait_time` 模拟真人思考间隔——能写多步骤有状态的行为（建房→收事件→投票），这是 wrk/ab（只能打固定 URL）做不到的
- **并发模型**：底层 gevent 协程，单进程几千并发用户（用户大部分时间在等响应，协程切换开销小）；到天花板就走 `--master`/`--worker` 多机分布式
- **选型对照**：固定接口测极限 → wrk/k6；复杂有状态行为 → Locust；GUI 拖拽老牌 → JMeter。工具服务于场景，S3 长连接场景如压不动再单补 k6
- **关联代码**：`bench/locustfile.py`（S1ApiUser 就是一个虚拟用户的定义）

### C05 一致性哈希与哈希盐陷阱（2026-08-11 · D-3 组）

- **要解决的问题**：房间 Actor 是单写者，状态活在**某一个进程的内存**里。多节点部署后，请求必须被送到那个进程——需要一个所有节点都能算出同一答案的函数：`房间 ID → 归属节点`
- **为什么不用取模**：`hash(game_id) % N` 的分母是**节点数**。3 台扩到 4 台，分母从 3 变 4，约 3/4 的房间换主。而房间迁移意味着状态转移 + Actor 重建，迁移量就是代价本身
- **环的做法**：把哈希空间首尾相接成一个环（0 ~ 2^128），节点和房间都映射到环上某点，房间顺时针找到的第一个节点就是归属。**分母是环本身，不是节点数**——摘掉一个节点，只有它那段弧上的房间受影响，期望迁移量 1/N
- **虚拟节点**：3 个物理节点把环切成 3 段随机长度的弧，倾斜很严重（可能 60%/30%/10%）。给每个物理节点在环上放 160 个虚拟点（`node#0`~`node#159`，libketama 的经典取值），靠大数定律把弧长摊平——实测分布偏差约 5%
- **关键陷阱：不能用内置 `hash()`**。CPython 对 `str` 的 `hash()` 带**每进程随机盐**（`PYTHONHASHSEED`），同一个字符串在不同进程算出不同值。后果不是"结果略有差异"，而是**每个节点的路由表都不一样 → 同一个房间被两个节点同时认领 → 单写者模型作废、状态分叉**。改用 md5（取分布性，不取密码学强度）。凡是跨进程比较的哈希都适用：路由、分片、去重、缓存键
- **虚拟节点名必须是派生的而非随机的**：`f"{node}#{i}"` 由节点名算出来，所以节点重启后落在环上的还是同一批位置，名下房间会漂回来。用随机数就丧失了这个性质
- **关联代码**：`backend/app/core/hash_ring.py`；`backend/tests/test_hash_ring.py::test_hash_is_stable_across_processes`（起子进程重算哈希做断言，这是唯一能抓到盐陷阱的测法）

### C06 心跳租约式故障检测（2026-08-11 · D-3 组）

- **一句话**：判活不靠主动探活，靠**节点自己上报**——"最后一次心跳早于 TTL"即视为死亡。k8s node lease、Nacos/Eureka 注册续约、Kafka session timeout 都是这个结构
- **为什么不主动探活**：探活方要维护 N×N 的探测关系，且"探不通"分不清是对方死了还是网络分区。自上报把判断压缩成一次时间戳比较
- **集群时钟必须是单一共享源**：判活是"拿 A 机器写的时间戳，和 B 机器的现在比"。若各用本地时钟，机器间时钟偏移会**直接变成误判**——快 10 秒的节点看谁都像过期，慢 10 秒的节点写的心跳一出生就过期。用 Redis `TIME` 作为集群唯一时钟即无此问题
- **阈值是不对称代价的取舍**：`NODE_TTL = 3 × HEARTBEAT_INTERVAL`。误摘一个活节点 → 它名下房间被别人认领，而它内存里还握着状态 → **双写**；这比晚几秒发现宕机严重得多。所以宁可保守
- **为什么用 ZSET 存**：member = node_id，score = 最后心跳时间。对比方案——纯 SET 没有成员级 TTL，死节点永远留着；每节点一个 TTL key 可以自动过期，但列举存活节点要 SCAN 整个 keyspace（生产慢操作）。ZSET 一次 `ZRANGEBYSCORE` 取存活集合，一次 `ZREMRANGEBYSCORE` 清死节点。延时队列、滑动窗口限流是同一个套路
- **身份与地址要分开存**：node_id 决定房间归属（进环），地址只是转发用的联系方式。节点换 IP 不该引起房间迁移，所以 ZSET 存身份、HASH 存地址
- **关联代码**：`backend/app/core/node_registry.py`；`backend/tests/test_node_registry.py`（跑真 Redis，替身只能测出替身自己的 ZSET 语义）

### C07 分位数的样本量前提，与 max 为什么不能当指标（2026-08-11 · D-3.5）

- **一句话**：**P99 是"第 99% 名那个样本"，所以它的可信度由样本量决定**。n=200 时 P99 就是第 2 名，等于在报单个离群值；n=2000 时才真的是第 99%
- **推论（这次真踩到）**：切分维度越细，每格样本越少。按接口分开看 P99 是**排障视角**（定位哪条路径慢），按同类接口合池看才是**容量视角**（系统对用户的承诺）。写对外材料用后者，且**必须同时报 n**
- **max 为什么最不稳**：max 就是"最差的那一个样本"，没有任何平滑，样本越多越容易出现更大的值。同条件复测能轻松翻倍（实测 187ms → 411ms）。要讲改善量级讲 P99 或 P50，不讲 max
- **分位数有多种定义**：最近秩法（第 `ceil(p*n)` 个样本，不插值）、线性插值法、分桶估算法（locust CSV 与 Prometheus Histogram 都是这种，见 C03）。**换算法数字就会变**，所以报数字要注明口径
- **失败请求不能混进延迟分位数**：失败请求的耗时通常是超时阈值（30s），混进去算出的 P99 反映的是超时配置而不是系统延迟。分位数只统计成功请求，失败单独报失败率
- **原始值必须留档**：只存聚合结果，事后想换口径（换分位数定义、换切分方式、补 P999）就得重跑压测。我们把原始样本存成 `bench/results/*_latency_raw.json`
- **关联代码**：`bench/locust_s2.py` 头部的原始延迟采集器（`events.request` 采样 + `events.quitting` 落档）

## 2026-08-12 · H-3c·下（资源层限流：AI 队列深度上限 → 自动降级）

### 038 这一层过载时不能拒——拒一个 AI 回合等于让房间永久卡死；漏账的计数器会让系统永久停在降级态

- **现象/起因**：三层限流的最后一格。前面三处（网关层拒 HTTP、应用层拒建局、房间层拒动作）都有一个共同前提：**对面有客户端，它会拿到错误码、会重试**。AI 回合**没有这个前提**——一个 AI 回合被丢掉，就没有任何人会再来提交它，那个房间的阶段永远不推进，**房间不是变慢而是永久卡死**。所以这一层的过载响应只能是**降级，不能是拒绝**。这是"限流"这个词容易误导的地方：**限流的手段是拒绝，但过载控制的目的不是拒绝**，到了没有重试方的地方就必须换手段。
- **降级降的是"每个任务多贵"，不是"放几个任务进来"**：积压的成因不是任务条数多，而是**每条都要等一次 LLM**（十几秒量级）。同样长的队列，走规则引擎每条是毫秒级——**队列长度一点没变，排空时间差三个数量级**。所以过载时把 LLM 摘掉：对局照常进行，AI 说话变套路。大白话：堵车时不是把车赶走，是让每辆车少占路。这也正是 5 级降级矩阵里 L2（AI 全切规则引擎）那一级，只不过这里是按队列深度**自动**触发的。
- **做法**：`core/ai_queue.py`。投递侧 `enter()` 登记一笔"在飞任务"并把 token 随 Celery 任务带下去，worker 跑完 `leave_sync()` 注销。worker 执行前读一次深度，超阈值就给 `AIService.get_action(force_fallback=True)`。指标 `aivalon_ai_queue_depth`（Gauge）+ `aivalon_ai_turns_degraded_total{reason}`。顺手接上了 `ai_queue_depth`——它和 H-2 那三个一样，声明在 `metrics.py` 但全代码库从没 `set()` 过。
- **深度必须在投递侧记账，不是等 worker 领到任务才记**。等领到才记的话，积压期间躺在队列里的任务一个都不算，**深度永远看着很小，而那恰恰是要看的东西**——积压的定义就是"投了还没被处理"。
- **降级判断放在 worker 里，不在投递侧**。投递到执行之间隔着排队，而积压期间那段间隔正是最长的；用投递那一刻的深度决定，等于**拿几十秒前的旧情况做现在的决定**。判断要放在离执行最近的地方。
- **不去问 broker 要 message_count**：`queue_declare(passive=True)` 最准，但那是一次**阻塞的 AMQP 往返**，加在每个 AI 回合上就是把 broker 挂进了热路径——**保护机制自己成了新的延迟来源**（同 H-1 那条：开关本地缓存必须有 TTL，否则就是把 Redis 挂在热路径上）。改成自己记账，代价是只覆盖"经由本项目投递的任务"，换来一次 Redis 命令拿到、且各进程看到同一个数。
- **最关键的选型：用 ZSET 存"在飞任务 → 投递时刻"，而不是 INCR/DECR 计数器**。worker 被 `kill -9` 就不会注销，纯计数器的**误差只会单向累积**——攒够阈值之后系统**永久停在降级态**，而且从指标上看不出来是漏账还是真积压（一条永远高位的曲线，无从分辨）。ZSET 在计数前先把超过租约时长的清掉：一个任务要么正常注销、要么被租约兜掉，**误差有上界且会自己消失**（同 C06 心跳租约）。**凡是"登记后要靠对方来注销"的计数，都必须假设对方不会来。**
- **租约长度有个下界**：必须大于单个 AI 回合的最坏耗时（LLM 舱壁上界 45s + 提交动作的往返），取 120s。小了会把**正在跑的**任务当成漏账清掉，于是深度永远上不去、降级永不触发——**一个"看起来在工作"的保护机制，实际从来没生效过**，而且不报错。这类"配小了会静默失效"的参数，测试要把关系钉住（本次有一条断言 `AI_QUEUE_LEASE > AI_LLM_TIMEOUT_SPEECH`）而不是钉死具体数值。
- **失败方向：读不到深度就报 0 = 不降级**。和限流器一致、**和 H-1 降级开关相反**：开关是人做的决定，读不到要保持已生效的降级态；这里的降级是**自动推断**出来的，推断不出来就别擅自降。判据是哪边的代价可恢复——误降是全站 AI 一起说套话（玩家看得见的产品退化），不降有 H-2 的 LLM 舱壁兜着（每次调用硬超时 + 自动回落，最坏慢一次）。**这是本项目第四种失败方向，四种都不一样：缓存放行回源 / 开关保持现状 / 限流器放行 / 自动降级不降。**
- **自动降级和人手开关刻意分成两个入口**（`force_fallback` 参数 vs `switches.ai_use_llm`）。混成一个的话，要么自动降级把人手切的开关覆盖掉（**人的决定被机器撤销**），要么反过来自动降级撤不回去。**一个每回合重新判断、一个要留到人来撤销，生命周期不同的东西不能共用一个状态位。** 对应地：人手开关刻意不设 TTL（H-1），而自动降级**必须**能自动恢复——`should_degrade` 只看当前深度、不留状态。
- **重试中的任务不注销**。`self.retry` 也会走 `finally`，但重试意味着这个 AI 回合**还没完成**；注销了的话，等待重试那段时间它不算在深度里，而**正在重试的任务恰恰是积压的一部分**——漏算会让深度在最需要它的时候偏小。
- **改任务签名要给默认值**：`queue_token: str = ""`。队列里可能还躺着上一版投递的消息，少一个参数就是一批 `TypeError` 直接进死信队列。**滚动发布期间新旧代码必然共存**，任务签名的兼容性和 API 的一样重要。
- **验收**：16 项单测（全量 255 项全绿）。压舱两条：`test_leaked_entries_expire_by_lease`（漏账被租约兜掉——这是选 ZSET 的全部理由）、`test_force_fallback_skips_llm_entirely`（降级后**仍然给出动作**，否则房间的阶段永远不推进）。`test_lease_must_exceed_worst_case_turn` 钉住那个静默失效的参数关系。
- **经验**：
  - **"限流"的手段是拒绝，但过载控制的目的不是拒绝**。判断能不能拒的标准很具体：**对面有没有一个会重试的客户端**。没有的话，拒绝就是永久丢失，只能改成降级。
  - **降级可以降"每个请求多贵"，不只是"放多少请求进来"**。本项目里这一刀把每个 AI 回合从十几秒压到毫秒级，队列长度一点没变而排空时间差三个数量级——**这类降级对用户的可见损失最小**（对局照常，只是 AI 说话变套路）。
  - **凡是"登记后要靠对方来注销"的计数，都必须假设对方不会来。** 加租约让误差自己消失；用纯计数器就是让误差单向累积，最终把系统永久钉在错误状态上，且不可分辨。
  - **判断要放在离执行最近的地方**，尤其当"决定"和"执行"之间隔着一个会变长的队列时。
  - **自动触发的机制必须能自动恢复，人工触发的必须留到人来撤销。** 两者生命周期不同，共用一个状态位一定会出现"人的决定被机器覆盖"或"机器的决定撤不回去"。
  - **自动降级尤其必须可观测**：人手切开关时至少有人知道自己切了，按深度自动触发的降级**没人按过按钮**——不上报的话"AI 怎么突然说套话了"在复盘时无从查起。

## 2026-08-12 · H-3c·上（资源层限流：单房间队列上界 + 动作等待上界）

### 037 前两层限流统计不到"一个房间被打爆"；超时不丢弃排队中的动作，等于让客户端重试一次就生效两遍

- **现象/起因**：网关层（系统总容量）和应用层（单用户配额）都做完了，但两层**全通过的流量照样能压死一个房间**。同一房间的动作在一个 Actor 队列里串行执行，8 个人（或 8 个脚本）对着一局猛点，每个人都没超自己的 1 次/秒，队列却能排到几千个，而排在队尾的人要等前面全部跑完。这是个**资源维度**的问题：按用户统计不出来，按 IP 也统计不出来，只能在**持有该资源的地方**设上界。大白话：前两层管的是"总共放多少人进商场"和"每个人限购几件"，这一层管的是"这一个收银台前面最多站多少人"——商场不挤、也没人超量买，一个收银台照样能排到关门。
- **原来的实现有两个缺口**（都是 todo 里挂着的"已知不修"）：`asyncio.Queue` 无界，队列想排多长排多长；`submit` 是裸 `await future`，**处理函数卡住就永久挂住**，而挂住的是一个 HTTP 请求，连接一直占着。两个缺口互相独立，所以两个上界都要——队列不满但每个动作都慢时，队尾一样在无限等。
- **做法**：`RoomActor` 上加两条上界。队列满抛 `RoomOverloaded`（路由层转 503 + `Retry-After`），等待超时抛 `RoomActionTimeout`（转 504）。指标 `aivalon_room_overload_total{reason}` 分 `queue_full` / `timeout`。
- **先判满再入队，不用有界 Queue 的 `await put`**：有界队列靠 `put` 阻塞也能限长度，但那是**让提交方排在队列外面等**——队伍只是从看得见的地方挪到了看不见的地方，延迟照样无上限。过载时最不该做的事就是让调用方多等，它的连接、协程都还占着，**等待本身就是资源**。要的是当场拒绝。
- **最要紧的一条：超时后还没出队的动作必须丢弃**。`wait_for` 超时会取消它等待的那个 future，Actor 出队时据此判断"提交方还在不在"，`future.done()` 就跳过不执行。不这么做的话：客户端拿到超时 → 按超时语义重试 → 服务端把排队里的那次也跑了，**一个动作生效两遍**。投票、提名重复执行会直接把对局算错。这也是队列上界的另一半价值——**过载时队里堆的多半都是已经没人等的动作**，挨个执行完只是在给一个已经过载的房间继续加活。
- **两种拒绝的语义必须分开，不能合成一个异常**：`queue_full` 是**压根没入队，所以一定没生效**，可以放心让客户端重试（所以给 503 + `Retry-After`）；`timeout` 是**可能已经在执行了，服务端无法断言**（已经在跑的拦不住），所以给 504——客户端拿到 504 应该先拉一次状态再决定重不重试，要安全重试就带幂等键。**错误码要如实反映"这次到底做没做"，而不只是"失败了"。**
- **顺手修掉两个原来就存在的竞态**（todo 里"Actor 空闲退出竞态"那条）：
  - **空闲判定与新动作入队会撞车**。`wait_for` 超时已经取消了 `queue.get()`，紧接着 `put_nowait` 把动作放进队列——**没人取它，它的 future 永远不完成**。在 submit 有超时之前这是个永久挂起（正是上面那个缺口放大了它）；有超时之后是一次无理由的 504。修法是退出前再看一眼队列，非空就 continue。
  - **注销必须比对身份，不能按 game_id 盲删**。老 Actor 的退出回调可能晚于新 Actor 建好（同一房间又来动作了），按 id 直接 pop 会把**正在用的**那个删掉，下次动作再建第三个，同一房间短暂存在两个写者——**单写者模型（去掉分布式锁的全部依据）就破了**。同理 `get_or_create` 不能把 `closed` 的 Actor 交出去，交出去调用方一 submit 就把它的 `_run` 重新 create_task 救活。
- **验收**：11 项单测（全量 239 项全绿）。压舱的是 `test_timed_out_action_is_dropped_if_not_yet_started`（放弃等待的动作不能被执行）和 `test_queue_full_rejects_instead_of_queueing`。`test_queue_recovers_after_drain` 盯"拒绝不是粘性的"——这一层拦的是瞬时风暴，不是惩罚房间，粘住不放就变成"一次抖动导致对局打不下去"。两个竞态各有一条测试钉住。写测试时自己踩了两次同一个坑：占位用的那个 submit 也跟着共享了短超时，于是 timeout 计数多加一次——给它单独传 `timeout=` 才对。
- **经验**：
  - **限流要分层，是因为每层能看见的东西不同**。网关层只看得见总量，应用层只看得见"谁在调"，**"哪个资源被打爆了"只有持有资源的地方看得见**。三层各拦一类，谁也替代不了谁。
  - **有界队列不等于有上界的延迟**。靠 `await put` 挡住的请求还在等，只是等在别处。过载控制的目标是**尽快给出否定答复**，不是把队伍藏起来。
  - **超时必须连带"取消尚未开始的工作"**，否则超时就成了重复执行的入口。判据是"提交方还在等吗"，而 `wait_for` 取消 future 恰好提供了这个信号——所以别把它换成 `shield`/`gather`。
  - **失败要区分"确定没做"和"不确定"**，并且如实映射到错误码（503 vs 504）。含糊其辞的失败会把重试的决定推给客户端去猜。
  - **对象的注销要比对身份而不是比对键**。"我这个 id 该退出了"和"这个 id 现在归我"是两件事，中间可能已经换了人。同类问题在租约、连接池、会话管理里都会出现。

## 2026-08-12 · H-3b（应用层限流：固定窗口换滑动窗口 + 补齐遗漏路由）

### 036 固定窗口在边界能挤进 2 倍，把业务承诺打了对折；限流键读 `X-Forwarded-For` 等于没有限流键

- **现象/起因**：H-3a 做完网关层后回头看应用层，本以为"按用户限流早就有了"，一读实现发现两个真问题。第一个是**算法**：去读 `fastapi-limiter` 的 Lua，是 `SET key 1 px` + `INCR`——**固定窗口**，key 从**第一个请求**起算过期，到点整批清零。于是窗口边界可以被利用：上小时最后一秒建 10 局、下小时第一秒再建 10 局，**2 秒内建了 20 局，而每一次都"没超过 10 局/小时"**。业务承诺被算法的实现细节打了个对折。大白话：固定窗口是"每到整点清零"，卡着点前后各来一波就能翻倍;滑动窗口是"往前看一小时"，没有"整点"这个可利用的东西。
- **第二个问题更要紧，是个真漏洞**：`fastapi-limiter` 的 `default_identifier` **读 `X-Forwarded-For`**，而那是个客户端可以随便填的请求头。项目里 `send-code` 和 `login` 两个路由**没传 identifier**，用的正是这个默认实现——也就是说**最需要限流的两个接口，限流键可以伪造**：每个请求换一个假 IP，就能无限发验证码（**每封邮件都花真钱**）、无限试密码撞库。**一个可伪造的限流键等于没有限流键。** 只有确实有一层自己可信、且会**覆写**该头的代理时才能信它，那属于部署配置，不该由应用库默认假设。
- **顺带发现覆盖面也不够**：原来只有建局和提交动作两个路由挂了限流。`register`（往库里写一行）、榜单、回放、历史、对局快照全都没有。这次一并补上，并按"这个操作多贵"和"真人能多快"分档——**不是所有接口配一个数**：发码 3 次/小时（花钱），登录 10 次/5 分钟（撞库目标），注册 5 次/小时，读接口 60 次/分（有缓存、打进来不贵，拦的是脚本抓取）。
- **做法**：新写 `core/sliding_window.py`（滑动窗口日志，ZSET{member=uuid, score=Redis 时刻}），把**所有**限流器统一到它上面，`rate_limit.py` 退化成"配置入口"（各接口的 scope 与阈值）。刻意统一而不是新旧并存——**留两套限流机制比留任何一套都糟**，读代码的人得先判断这个路由用的是哪套才知道边界行为。
- **为什么两层用不同算法**（不是随手换）：网关层要的是**突发容忍度和稳态速率能分开调**（平时闲、偶尔涌入），令牌桶恰好两个旋钮；应用层承载的是**业务承诺**，"10 局/小时"必须真的是 10 局/小时，需要的是没有可利用边界。**选算法的依据是"要什么性质"，不是哪个更先进。**
- **滑动窗口的代价和它的上界**：日志把窗口内每次请求都记一条，内存 O(窗口内请求数)，看着像风险——但**先 trim 再计数、超了就不写入**，所以 ZSET 长度上界就是 `times` 本身。这也划定了适用范围：`times` 小（1/秒、10/小时）时很划算；`times` 很大（网关层 200/s）就该用令牌桶——**令牌桶只存 2 个数字，与流量无关**。
- **三个容易写错的细节**：
  - **trim 必须在计数前**。先计数会把已滑出窗口的算进来，限流比设定的更严；而且不 trim 的话 ZSET 随请求数无限长大。
  - **超限时刻意不写入**。写了的话每次被拒都把窗口往后推一次，**一个还在重试的客户端会把自己永久锁死**，永远等不到解封。惩罚性延长是另一回事，要做也该显式做，不该是限流的副作用。
  - **member 必须唯一，用 uuid 而不是时间戳**。ZSET 里 member 相同会被当成同一条覆盖掉，用时间戳的话同微秒的两个请求只算一条——**并发越高漏计越多，限流器恰好在压力最大时失效**。score 才是跨进程比较的基准，所以它取 `redis.call('TIME')`（同 H-3a 与 C05：节点时钟偏差会变成窗口边界偏差）。
- **验收**：15 项单测（全量 228 项全绿）。压舱的是 `test_window_has_no_exploitable_boundary`：窗口过半时仍必须拒（固定窗口此刻已清零），最早那批滑出后才恢复——这一条就是换算法的全部依据。`test_rejected_requests_do_not_extend_the_window` 盯"重试不能把自己锁死"，`test_unique_members_so_same_instant_requests_all_count` 盯 uuid 那条（20 个同瞬间并发必须各计一条）。另外把 `test_room_router.py` 里那条"转发豁免"的旧测试挪到了新机制上——**要保护的是行为，不是某个具体的类**。
- **经验**：
  - **限流器的边界行为取决于算法实现，而不是你写的那个数字**。"10 局/小时"这句业务承诺，用固定窗口实现出来实际是"最多 20 局/小时"。用之前先读一眼库里的 Lua。
  - **限流键的可伪造性比阈值重要得多**。阈值配错了只是宽严不当，键能伪造是这一层直接失效。凡是从请求头取的东西都要问一句"客户端能不能自己填"。
  - **阈值该由"这个操作多贵"和"真人能多快"共同决定**，不是全站一个数。花钱的（发邮件）最紧，写库的次之，有缓存的读接口可以很宽。
  - 换机制时**统一到一套**，别新旧并存。并存的代价是每次读代码都要先判断"这条路由走的是哪套"。

## 2026-08-12 · H-3a（网关层准入：全局令牌桶 + IP 令牌桶）

### 035 按用户限流保护不了系统；限流器的失败方向是放行，而且它自己很容易变成放大器

- **现象/起因**：项目里早就有限流（`rate_limit.py`，按 user_id 的固定窗口，挂在建局和提交动作两个路由上），但它保护不了系统。**一万个用户每人只建 1 局，完全合规，机器照样倒。** 按用户限流表达的是**业务规则**（"这个用户别太频繁"），而过载要防的是**总量**（"这台系统一共能吃多少"）。这是两层不同的东西，谁也替代不了谁。大白话：业务层是"每人限购两件"，网关层是"店里只能站 200 人，满了在门外等"。
- **为什么不复用 fastapi-limiter 的固定窗口**：固定窗口在窗口边界能放进 **2 倍** 流量（上一窗口末尾 N 个 + 下一窗口开头 N 个），而准入层的存在意义恰恰是给出一个可信的容量上界。更要紧的是固定窗口**表达不了"允许突发到 400、但稳态只给 200/s"**——而这正是真实流量的形状：平时很闲，偶尔一波集中涌入。令牌桶把这两件事拆成两个独立旋钮：`capacity` = **允许多大的突发**，`rate` = **稳态速率**。固定窗口只有"N 次/秒"一个旋钮，做不到。
- **必须用 Lua**：「读桶 → 算补了多少 → 判断 → 写回」是个读改写序列，而多个 API 进程共享同一个桶。`GET` 再 `SET` 的话，两个进程同时读到"还剩 1 个令牌"，各自都放行——桶被超发。Lua 在 Redis 里单线程整段执行，这个序列才原子。
- **时间基准取 Redis 的，不取调用方的**：补令牌要算"距上次多久了"。用各 API 节点自己的 `time.time()`，**节点间时钟偏差会直接变成令牌数偏差**——快的那台算出更多令牌，等于给自己多发配额。脚本里用 `redis.call('TIME')`，桶的时间基准和桶本身在同一个地方。**共享状态的时间基准也是共享状态**，同 C05 那条"跨进程比较的哈希不能用带随机盐的 `hash()`"，是一类问题：凡是多个进程要算出同一个答案的输入，都不能各自本地取。
- **失败方向：读不到 Redis 要放行**。限流器是**保护机制，不是可用性依赖**。Redis 抖一下就把全站拒了的话，这个限流器本身成了新的单点，**它造成的故障比它防的还大**。注意这和 H-1 降级开关的方向**恰好相反**（开关读不到要保持已生效的降级态）：开关表达"人做的决定不能自己失效"，限流器表达"别帮着把故障放大"。**每个有兜底的地方都要单独想一遍失败方向，照抄隔壁就会写反**——这已经是这条经验第三次以不同形式出现了（缓存放行回源 / 开关保持现状 / 限流放行）。
- **三处"限流器自己变成放大器"的坑，都是加防护时顺手能种下的**：
  - **`/health` 必须豁免**。突发下把健康检查也拒了，负载均衡认为节点已死并摘掉它——剩下的节点承接更多流量、更快被拒，**限流器亲手把一次过载放大成雪崩**。`/metrics` 同理，正过载时最需要看指标。
  - **429 必须带 `Retry-After`**。不告诉客户端等多久，它会立刻重试，**过载期间的重试本身变成新的流量峰值**。
  - **被 IP 层拒掉的请求不能扣全局桶**。扣了的话一个刷接口的 IP 就能把全局配额一起烧掉——而那正是它想干的事：自己被拒无所谓，只要能顺带吃掉别人的容量。
- **另外两个决定**：
  - **不读 `X-Forwarded-For`**。它是个请求头，客户端可以随便填。信了它，每个请求换一个伪造 IP 就让 IP 桶形同虚设——**一个可伪造的限流键等于没有限流键**。只有确实有一层自己可信、且会**覆写**该头的代理时才能信，那属于部署配置，不该由应用默认假设。
  - **中间件顺序**：Starlette 里后加的在外层，所以刻意让 TraceId 包在准入外面——被拒的 429 也要有 trace_id 和访问日志，否则"某个客户端什么时候被限了"在复盘时查不到，而这恰恰是限流最需要解释清楚的事。
  - **桶的 TTL 按"恰好攒满"设**：`cap/rate` 秒。这是无损的，因为**一个过期消失的桶和一个满桶完全等价**（都是下次来了给满配额），顺手解决了 IP 桶随访客数无限增长的问题。
- **验收**：12 项单测（全量 213 项全绿）。`test_concurrent_checks_do_not_oversubscribe` 是 Lua 那条的全部依据——30 个并发打 10 个令牌的桶，放行数必须**恰好** 10；`test_ip_rejection_does_not_burn_global_quota` 盯"刷的 IP 不能吃掉别人容量"；`test_refill_never_exceeds_capacity` 盯攒令牌要封顶（不封顶的话通宵没流量会积压出几万个令牌，**突发上限就成了"闲了多久"的函数**）。写这个测试时我自己先写错了一版：桶不存在时 `peek` 直接返回 `cap`，所以得先消耗一次把带时间戳的桶建出来，否则测不出"攒过头"。
- **阈值目前是拍的**（全局 400/200 QPS、单 IP 60/20 QPS），等 S4 复测出真实拐点再回来定——按 AGENTS.md 铁律，先基线后调参。
- **经验**：
  - **限流分层的依据是"保护对象不同"**：业务层保护业务规则（按 user_id），网关层保护系统容量（按总量和来源）。只做一层的话，要么合规流量压垮机器，要么合理用户被误伤。
  - **令牌桶 vs 固定窗口的选择标准不是"哪个准"，是"要不要把突发容忍度和稳态速率分开调"**。要，就只能是令牌桶。
  - **加防护的时候要专门问一句"它自己会不会变成放大器"。** 健康检查、重试指引、拒绝时的副作用，这三处都是加限流时顺手就能种下的雪崩源。
  - 凡是多进程要算出同一个答案的输入（哈希、时间、随机数），都不能各自本地取。

## 2026-08-12 · H-2（LLM 舱壁：整次调用限时 + 超时回落规则引擎）

### 034 "我传了 timeout" 和 "这次调用有上界" 是两回事；超时不能上抛成任务失败

- **现象/起因**：`ai_service` 早就有 `except` 回落规则引擎，看着挺完整——但 LLM **卡住**而不是**报错**的时候，那个 `except` 永远不会进。于是去确认超时到底兜住没有：`llm_service` 把 `timeout` 直接传给了 OpenAI SDK，看着像"最多等 45 秒"。读 `openai/_base_client.py` 才发现完全不是：SDK 的 `timeout` 是**单次尝试**的（`:1058` `for retries_taken in range(max_retries + 1)`），`DEFAULT_MAX_RETRIES = 2` 也就是最多打 3 次，重试之间还有 `time.sleep(backoff)`（`:1174`）。**`timeout=45` 的真实上界是 140 秒以上。** 大白话：以为定了"最多等 45 秒"，其实定的是"每次最多等 45 秒，一共问三次"。
- **根因**：**把上界外包给了依赖库的一个参数，而没验证那个参数的语义。** 代价不只是等得久——调用方按 45 秒做的容量估算全是错的（AI 队列并发、玩家等待预期、Celery 任务软超时），一个参数的语义误会顺着往上污染了一整条链的容量假设。
- **做法两处**：
  1. **`asyncio.wait_for` 包住整次调用**，它才是权威上界。放最外层的好处是不依赖 SDK 的任何语义——SDK 换版本、重试策略改了，这个上界还成立。**超时要卡在自己的代码里。**
  2. **`max_retries=0`**。重试适合"答案很重要且错误是暂态的"；而这里**已经有一个立刻可用的次优答案**（规则引擎）。等 3 次 LLM 的时间里规则引擎能出 3 次结果，玩家还不用干等。**有廉价兜底可用时，重试的价值是负的**——它花掉的是玩家的等待时间。
- **超时往哪边倒：返回 `{"error": ...}`，绝不上抛**。抛出去会被 Celery 当任务失败、按退避重试 5 次，而重试打的还是那个慢掉的 LLM——**把一次慢放大成五次慢**，还顺手占满 ai_queue 的并发。这是 H-1 那条"失败方向"经验的另一个方向：开关读失败要保持现状，LLM 调用失败要**立刻放手换兜底**。
- **一个必须靠顺序解决的坑**：`asyncio.TimeoutError` 在 3.11 起就是内置 `TimeoutError`，而它是 **`OSError` 的子类**，所以它**会被 `except Exception` 抓走**。超时那个分支必须写在 `except Exception` 前面，写反了不报错、只是所有超时被记进 `error` 档——**指标静默地失真，比崩掉难发现得多**。（`asyncio.CancelledError` 相反，不是 `Exception` 子类，同 029。）
- **顺手补上了一个空指标**：`llm_calls_total` / `llm_latency` 在 `metrics.py` 里声明了但**全代码库没有任何地方 `inc()` 过**，这次的 `llm_service` 是第一个真正写它们的地方。声明了没接的指标等于没有指标，而且比没有更坏——面板上有这条线、永远是 0，看的人会以为"没调用"。
- **指标口径两条**：
  - **失败和超时的耗时也要记**。只记成功的话，**LLM 全在超时的时候这条曲线反而会变好看**（慢的都没被统计），最需要告警的那一刻指标一片绿。这类"越坏越好看"的指标比没有指标危险。
  - **四档分开记**：`success` / `timeout`（依赖**慢了** → 降级或扩容）/ `invalid`（依赖**坏了**，通了但返回的不是合法 JSON → 去改 prompt）/ `error`（鉴权、配额、网络）。混成一个 "fallback" 档的话，事故里分不清该扩容还是该改 prompt。**指标分档的依据是"看到它之后要做的事不同"，不是"错误类型不同"。**
- **超时值提到配置**（`AI_LLM_TIMEOUT_SPEECH=45` / `AI_LLM_TIMEOUT_ACTION=20`）。发言给得宽是因为它要生成一整段话，投票/提名只输出几个数字、20 秒还不出就是不正常。提出来的意义是事故里可以压小——**"宁可 AI 说套话也别让玩家等"是个运行时可调的取舍，不该焊死在代码里**。
- **验收**：11 项单测（全量 201 项全绿）。`test_timeout_is_the_whole_call_not_one_attempt` 用一个永不返回的假 `_request` + 断言实际耗时 < 1s，盯的就是上界本身而不是"有没有传参数"；`test_latency_is_recorded_even_on_timeout` 盯"越坏越好看"；`test_ai_falls_back_to_rule_engine_when_llm_times_out` 把舱壁和它真正要保证的事连起来——**舱壁的意义不是"调用失败得体面"，是"对局照常推进"**，AI 返回 None 的话这个玩家不动，而整局在等他。
- **经验**：
  - **"传了超时参数"不等于"有上界"。** 判断一次外部调用有没有上界，只问：这个参数约束的是一跳还是整次？重试次数和退避算进去了吗？拿不准就在自己代码里再包一层 `wait_for`——它不依赖依赖库的任何语义。
  - **有兜底时不要重试。** 重试的成本是等待时间，收益是"可能拿到更好的答案"；兜底越廉价，这笔账越亏。
  - **超时不要变成上层的失败。** 一层上抛、一层重试，慢会被逐层放大。想清楚"这次失败该在哪一层被吸收掉"。
  - 写 `except` 之前先确认异常的继承关系。`TimeoutError` 是 `OSError` 子类、`CancelledError` 不是 `Exception` 子类，这两条都会让"看着对"的 except 顺序悄悄错掉。
  - **声明了却没人写的指标要当成 bug**。它会让面板上出现一条永远是 0 的线，把"没有观测"伪装成"没有发生"。

## 2026-08-12 · H-1（AI 降级开关运行时可切）

### 033 需要重启才能生效的降级开关等于没有；开关的失败方向要偏向"保持已生效的决定"

- **现象/起因**：AI 走不走 LLM 由 `settings.AI_USE_LLM` 决定，而它是**启动时**从 `.env` 读一次的。想在事故里把 AI 切到规则引擎，就得改配置 + **重启所有 Celery worker**——而 AI 决策正跑在 worker 里，重启会把正在处理的 AI 回合一起打断。**一个需要重启才能生效的降级开关，在事故里等于没有**：降级的全部价值就是"不重启就能生效"，要重启的话不如直接扩容。这也是 H 组后面 5 级降级矩阵的前置——那 5 级每一级都得能热切。
- **做法**：开关值存 Redis（`switch:ai_use_llm`），各进程（API / worker / 网关）读同一个 key，一次写入全局生效；本地带一层 1 秒 TTL 的缓存。大白话：开关从"每台机器出厂时刻在壳子上的铭牌"变成"墙上一块所有人都看得见的牌子"，改一次全体照办。
- **两个 TTL 方向相反，这是设计里最容易写反的地方**：
  - **开关本身不设 TTL**。降级是人做的决定，不能自己到期弹回来——半夜降级完去睡觉，TTL 一到 AI 又开始打 LLM，那就是同一个故障再来一遍。要恢复必须显式删 key。
  - **本地缓存必须设 TTL**。开关每个 AI 回合都要读一次，每次都打一个 Redis `GET` 就是把 Redis 挂在了 AI 热路径上。TTL 就是"切换后最久多久生效"（同 `cache.py` 的口径：**TTL 是一致性上限**），取 1 秒——人手动切开关，等 1 秒和等 0 秒没区别。
- **根因/真正想清楚的那一点：读不到的时候往哪边倒**。Redis 读失败时**优先用本进程上次读到的值，哪怕它已经过期**，只有从来没读到过才退回配置默认值。这个顺序很要紧：开关被切到"已降级"往往正是因为线上在着火，而 Redis 抖动本身就是着火的一部分——这时候退回配置默认值（LLM 开着）等于**开关在最需要它的那一刻自己失效了**。**开关的失败方向要偏向"保持当前已生效的决定"，不是偏向出厂设置。** 这和缓存的失败方向恰好相反：缓存读不到要放行回源（F 组：缓存是加速器不是可用性依赖），开关读不到要保持现状——**两者失败方向不同，因为一个是"可以慢"另一个是"不能变"**。
- **其他几点**：
  - **默认值仍取自 `settings.AI_USE_LLM`**，开关只是多了一条运行时覆盖的通路，不是把原来那条换掉——压测和集成测试都靠 `AI_USE_LLM=false` 起环境（`bench/README.md`），换掉就把那套环境搞坏了。key 不存在 = 没人动过 = 用配置默认值。
  - **开关状态要上指标**（`aivalon_degrade_switch{name}`）。不上报的话复盘时分不清"AI 没说话"是因为降级了还是因为坏了——**降级动作本身必须可观测，否则它就是一次没人知道的静默变更。**
  - 只认登记过的开关名，拼错当场抛 `KeyError`。默默写进一个没人读的 key 的话，操作的人以为切了、实际什么都没发生——事故里这种"以为切了"比报错危险得多。
  - `redis_conn` 必须由调用方传进来，不能在 `ai_service` 里用全局单例：AI 决策跑在 Celery worker 里，那边每个任务新建一个 event loop，全局客户端会复用绑到已关闭 loop 的连接（`tasks/ai.py` 里原本就有这个注释，这次踩的是同一个坑的新入口）。
  - 操作入口 `/internal/switches`（GET/POST/DELETE）用和 `ai_action` 同一套 `X-Internal-Secret` 鉴权，`include_in_schema=False`。**这是改运行时行为的接口，不鉴权暴露出去它本身就是个可用性漏洞**；用内部密钥而不是用户 token，因为这不是"某个用户有权限做的事"而是"只有运维通道能做的事",授权来源不同。
- **验收**：11 项单测（全量 190 项全绿）。`test_switch_has_no_ttl` 盯的就是"不能自己弹回来"；`test_redis_failure_keeps_the_last_known_value` 是失败方向那条，先切降级、等本地缓存过期、再拿一个坏 Redis 去读，断言还是降级态；`test_ai_takes_rule_engine_branch_when_degraded` 把开关和它要控制的行为连起来——前面那些只验开关读写对不对，真正要保证的是"切了开关，AI 的分支真的变了"。
- **经验**：
  - 判断一个降级手段是否真的可用，只问一句：**生效需要重启吗**。需要的话它在事故里用不上。
  - 配置和开关是两种东西：配置是"这个部署长什么样"，开关是"现在这一刻我要它怎么行为"。前者可以启动时读，后者必须运行时可读可写。混在一起就会得到一个"需要重启的降级开关"。
  - **凡是有兜底默认值的地方，都要单独想一遍"失败时往哪边倒"**，而且不同机制的答案可能相反。缓存读不到往"放行"倒，开关读不到往"保持现状"倒。照抄另一处的写法就会写反。
  - 降级开关自己要能被观测和被查询（`GET /internal/switches` 同时给出当前值和默认值）。只显示当前值的话分不清"这是默认"还是"有人切成了这个"。

## 2026-08-12 · G-2（热榜读路径：分片 ZSET + 定时归并 Top N + 本地缓存）

### 032 分片键决定归并的复杂度，不只是数据摊在哪儿；"Redis 只负责排序"等于榜单 QPS 直接压在库上

- **现象/起因**：榜单读路径原来是"查 Redis 排序 → 拿着这批 id 去 MySQL 查用户名和场次"。Redis 只用来排序，**展示字段每次请求都回源**，所以榜单接口的 QPS 是一比一压在 MySQL 上的——缓存看起来加了，实际只挡掉了排序那一小半。
- **关键选型一：按 member 哈希分片，不是按写入轮转**。每个榜从 1 个 ZSET 变成 8 个（`leaderboard:total_wins:s3`）。这个选择决定的不是数据摊在哪儿，而是**归并的复杂度**：
  - 按 member 哈希，一个玩家的分数**完整待在它自己那一片里**，于是「全局 Top N」一定包含在「各片 Top N 的并集」里——某人排全局前 N，那他所在片里最多也只有 N-1 个人比他高，他必然在这片的 Top N 内。归并只要每片各取 N 条，读 `SHARDS × limit`（8 × 10 = 80）行，**这是个与总人数无关的上界**。
  - 反过来按写入轮转分片（图省事让每次写落在随机一片），同一个人的分数被**拆散在多片**，必须把所有片的所有成员加起来才能排序——那就是全表扫。**分片键选错了，读路径就没有便宜的归并可用。**
  - 大白话：按人分片就像按姓氏把档案柜分成 8 抽，找"全校前十"只要每抽翻最上面十份；按轮转分片等于每次随手塞进一个抽屉，同一个人的成绩散在 8 处，非得全翻一遍才知道谁第一。
- **为什么不用 `ZUNIONSTORE`**：它要把所有片的**全部成员**并起来，开销随总人数走，而且是在单线程的 Redis 里跑，会把别的命令一起堵住。改成"每片取 Top N，拿回应用侧排序"，开销是 `O(SHARDS × limit)`，而且这点 CPU 花在**无状态可横向扩的应用进程**上，不占 Redis 那唯一一条线程。
- **关键选型二：定时归并，不是读时归并**。归并循环每 `MERGE_INTERVAL` 跑一次，把结果连**展示字段一起烤进一个快照 key**。于是：
  - **归并次数由间隔决定，和读 QPS 无关**——这是"定时归并"相对"每次读都归并"的全部意义。指标 `rank_reads{result="merged"}` 应该几乎不涨，它一旦跟着读 QPS 走，就说明归并循环没在跑。
  - 读路径**一次 MySQL 都不查**：用户名、场次、胜率在归并时就查好写进快照了，查库从"每次请求一次"变成"每 `MERGE_INTERVAL` 最多一次"。
  - 大白话：以前每个来看榜的人都自己去八个抽屉里翻一遍再跑去教务处抄一遍名字；现在是每 5 秒有人整理一张榜贴在墙上，来看的人只看那张纸。
- **根因/坑**：
  - **快照按最大 limit 存一份，切片在应用侧做**。按 limit 分别存就等于让缓存 key 跟着请求参数走，而 `limit` 是个 1..100 的无界维度——同 C02 label 基数那一类问题：**凡是让请求参数进 key 的地方，都要先问这个参数的取值空间有多大。**
  - **分片必须用 md5 不能用内置 `hash()`**。`hash()` 受 `PYTHONHASHSEED` 影响、每进程不同，而**写入的进程和归并的进程不是同一个**——写进 s3 的人在 s5 里被找，等于数据凭空消失，同 C05 那个盐坑。
  - **归并循环刻意不做互斥**，和写路径的 `RENAME` 换出恰好相反：归并是纯读 + 覆盖写，多节点重复做只浪费点 CPU，不会算错；换出重复做会丢增量，那才必须互斥。**该不该加互斥，看重复执行会不会改变结果，不看它是不是"后台任务"。**
  - `get_leaderboard` 走 `cache.get_or_load` 复用 F-1 的 L1 和 F-4 的 singleflight，但**刻意传 `redis=None`**：快照本身就是这份数据的 L2，再让 cache 往 Redis 写一份信封就是同一份数据存两处，而且两处失效时机还不一样。
  - 榜上有人但库里查不到（注销）就跳过，不留空位——榜是派生数据，以 MySQL 为准。
- **解决**：`rank_buffer.py` 加分片（`shard_of`/`key_for_member`/`shard_keys`）和 `merge_shards`；`rank_service.py` 加快照层（`rebuild_snapshot` / `_read_snapshot` / `merge_loop`），`_rebuild_leaderboard` 重写成按分片的 `rebuild_from_db`；归并循环挂在 API 进程 lifespan 上；`routers/users.py` 那段"拿 id 回库拼装"整段删掉。两处 DB 查询抽成 `_load_users` / `_load_all_scores`，一是它们是读路径上唯一碰库的地方、抽出来才看得清，二是测试要替掉它们才能验"读路径不碰库"。
- **验收**：16 项新单测（全量 179 项全绿，`tests/` 目录下）。最要紧的是 `test_merge_matches_full_scan`：500 人随机分数，归并结果必须和"全量扫描再排序"逐条一致——**这条就是按 member 分片这个选择的全部依据，换成轮转分片它会红**。另外 `test_reads_never_touch_db_once_snapshot_exists` 连 L1 都清掉、读 20 次，断言查库次数还是 1，这是这组优化的核心口径；`test_rebuild_from_db_heals_overcounted_scores` 把分数手动改高再对账，验的是 G-1 敢用不幂等 `ZINCRBY` 的那个前提。
- **经验**：
  - 说"用 Redis 做了排行榜缓存"之前先问一句：**展示字段是从哪来的**。Redis 只负责排序、字段还回源的话，QPS 该压在库上还是压在库上。
  - 分片先想清楚读路径怎么归并，再定分片键。**分片键的选择约束的是查询形态**，跟"数据分散开"这个直觉关系不大。
  - 把周期性任务的开销从"每次请求一次"挪成"每个间隔一次"，是缓存之外另一条独立的杠杆：它换掉的是**开销和流量的耦合关系**，不是单次开销的大小。
  - 后台任务要不要互斥，判据是"重复执行会不会改变结果"。同一个项目里两个都是"每隔几秒跑一次的循环"，一个必须互斥、一个刻意不互斥，原因全在这句上。

## 2026-08-12 · G-1（热榜写路径：MQ + 批量合并 ZINCRBY）

### 031 "用增量还是绝对值"决定了要不要读一次数据源；顺手发现胜负判定一直是错的

- **现象/起因**：原来的写路径是每局结束都去 MySQL 查一遍这几个玩家的**绝对**胜场，再 `ZADD` 覆盖榜上的分数。一局 8 人 × 3 个榜 = 24 次 `ZADD`，外加一次查库，全都发生在对局结束那一刻；200 局同时结束就是 200 次查库 + 几千次往返，而且这些往返打的正是读路径在用的 ZSET。
- **关键选型：`ZADD` → `ZINCRBY`，省掉的不是一条命令而是那次查库**。`ZADD` 写的是绝对值，所以**必须先知道现在是多少**——那次 MySQL 查询就是这么来的。`ZINCRBY` 写的是增量，而增量在对局结束那一刻就已经知道了（赢了就 +1），根本不用查。**"用增量还是绝对值"决定了要不要读一次数据源，这不只是 API 差别。**
  - 代价是增量不幂等：绝对值 `ZADD` 重复执行没事，`ZINCRBY` 重复执行就多加一次。这里接受 at-least-once，因为热榜是**可以从 MySQL 全量重建的派生数据**（`rebuild_from_db` 就是那条兜底路径，G-2 里把它按分片重写了），偶尔多算一次下次重建就正回来。换成账户余额这种权威数据就绝不能这么做。**能不能选 at-least-once，取决于这份数据有没有权威副本可以重建。**
- **合并缓冲**：增量先 `HINCRBY` 攒进一个 HASH（field = `榜|玩家`），后台循环每秒换出来批量刷。收益要分两笔说清楚，别混着吹：
  - **批量化是主要收益**：一个窗口里结束的所有对局攒成一次 pipeline，N 次往返变 1 次。和 Write-Behind 把 N 次 MySQL 写攒成一个事务是同一个套路。
  - **同 member 合并在本项目里其实不大**：一个人没法同时结束两局，所以同一个 (榜, 玩家) 在一秒内被改多次的情况很少。`rank_updates_buffered / rank_updates_applied` 会如实反映合并率是多少，不自己吹。
  - 顺带把 ZSET 的写从对局结束路径上摘下来了：读路径要用的 ZSET 每个窗口只被碰一次。
- **根因（真正的坑）**：
  - **换出必须用 `RENAME`，不能"`HGETALL` 之后 `DEL`"**。后者在两步之间进来的写会被 `DEL` 连带抹掉——那些增量既没上榜也不在缓冲里，**彻底消失且无从发现**。`RENAME` 是原子的，换出之后的写落进一个新的空缓冲，下一轮再刷。
  - `RENAME` 顺带解决了多节点互斥：每个节点都跑这个循环，但一个 key 只能被 `RENAME` 成功一次，抢输的直接拿到 `no such key`。**能靠单条命令的原子性做到互斥时就别再套一层分布式锁。**
  - **删除必须放在 `ZINCRBY` 之后**。中间宕机会让这批被重放一次（at-least-once）；反过来先删再打就是 at-most-once，会**永久少算**。两害取可以自愈的那个：多算的下次全量重建能正回来，少算的除了重建没有别的办法发现。
  - 临时 key 按节点分开，且每轮开头先捡上一轮的残批——`RENAME` 成功之后、`ZINCRBY` 打完之前崩掉的话，增量就躺在那个临时 key 里，不先处理就永久丢了。
- **顺手挖出来的既有 bug（和 G-1 无关，但不修就没法算增量）**：`stats.py` 里 `EVIL_CHARACTERS = {"ASSASSIN", "MORGANA", "MINION"}` 是**大写**的，而 `Character.ASSASSIN.value` 是小写 `"assassin"`，于是 `is_evil` **永远是 False**。后果：坏人赢了没人加分，好人赢了全场 8 个人（含坏人）都加分。**它不报错、不抛异常，胜负照样算得出来，只是全算错。** 改成比枚举不比字符串，集合和 `camp_of()` 一起提到 `game_enums.py`，让判据只有一处。
- **解决**：新增 `app/core/rank_buffer.py`（缓冲 + 换出 + 刷榜循环），挂在 API 进程的 lifespan 上（它是常驻定时循环，Celery 那边是任务驱动的，没有"每秒跑一次"这个语义）。`stats.py` 只负责算增量并入缓冲，那段"查库拿绝对胜场再 ZADD"整段删掉；顺带删掉为了调 `update_after_game_finish` 而拼的那个字段全填默认值的 `GameState`——那一步真正用到的只有 game_id、winner、人数三个值，换成 `record_finished_game(...)` 直接传。榜单 key 定义收敛到 `rank_buffer.BOARD_KEYS` 一处，`rank_service` 引用它而不是各写一遍字面量（写歪的表现是"榜看起来是空的"：写进了一个没人读的 key）。
- **验收**：13 项单测。判据是"ZSET 上最终的分数"和"发出去几条命令"。有两条是专门盯选型的：`test_zincrby_accumulates_across_windows` 跨两个窗口断言分数累加——用 `ZADD` 的话第二个窗口会覆盖第一个，**而这个错误只有跨窗口才看得出来，单窗口测不出来**；`test_writes_during_drain_survive` 手动 `RENAME` 模拟"刷到一半"，再写一笔，断言这笔不丢。全量 162 项全绿。
- **经验**：
  - 看到"先查出当前值，再写回去"就该停一下想想能不能改成增量操作。**读一次数据源的成本往往比那条写命令高得多**，而且这次读还发生在热路径上。
  - 攒批的收益要拆开算：是**批量化**（N 次往返变 1 次）还是**同 key 合并**（N 次变更变 1 次）？前者几乎总能拿到，后者要看业务上同一个 key 会不会被高频改。混着说就变成吹牛，指标口径也会跟着糊。
  - 换出型缓冲的正确性全在"原子换出"和"删除时机"两点上，和缓冲本身怎么攒无关。
  - 大小写不一致的集合比较是**静默失效**的典型：类型对、语法对、不报错，只是结果全错。凡是"字符串和枚举混用"的地方都该改成只比枚举——这和 F-5 的 `_decode` 不能用 None 当失败判据是同一类问题，**判据要能区分"没有"和"不是"**。

## 2026-08-12 · F-5（逻辑过期异步重建 + TTL 抖动，防雪崩）

### 030 逻辑过期把"回源"从请求路径上摘下来；抖动治的是雪崩会自我强化这件事

- **现象/起因**：F-4 的 singleflight 把 N 次并发回源压成 1 次，但**那 1 次还是有人在等**——热 key 过期瞬间，所有请求都得等那一次几十毫秒的查询回来。雪崩比这更狠一层：不是一个 key 过期，而是**一批 key 同时过期**（缓存刚被清空后重建的那批、同一次批量写入的那批），singleflight 是 per-key 的，一万个 key 同时过期就是一万次并发回源，它一次都挡不住。
- **两个机制分别治两件事**：
  - **逻辑过期治"要等"**。存进 L2 的不是裸值而是信封 `{"v": 值, "exp": 逻辑过期时刻}`，Redis 上的物理 TTL 比 `exp` 多留一个宽限窗口（`L2_GRACE=60s`）。于是出现一段"逻辑上已过期、物理上还在"的时间，读到它就**先把旧值返回、再派后台任务重建**——谁都不用等。像图书馆的书到了该换新版的日子，旧版不下架，谁来借都照借，同时后台去订新版；而不是先把书抽走、让借的人站着等新书到货。代价是这次读到的值最旧不超过宽限窗口，对回放事件流这种只增不改的数据完全可以接受。
  - **抖动治"会自我强化"**。物理 TTL 加 ±10% 随机偏移。关键不在于第一次雪崩，而在于**第一次之后幸存下来的 key 全被对齐到了同一个到期时刻，下一轮更整齐**——回源洪峰会周期性重现且越来越尖。随机化让到期时刻自然散开而不是越来越同步。
- **根因（真正的坑，两个）**：
  - **F-4 的二次检查 L1 会把重建变成空转**。逻辑过期那条路径为了让后续读命中，会把旧值填进 L1；后台重建任务一进 `_load_once` 就查 L1、拿到那份旧值、直接返回——**重建什么都没做，日志和指标却都显示它跑了**。这类 bug 不会报错，只会让机制静默失效。解法是给 `_load_once` 加 `skip_l1`：重建跳过 L1，但**照旧查 `_inflight`**（已经有人在回源就用它的结果，那份一定是新的）。跳过的只是 L1，不是 singleflight。
  - **不能用"值是不是 None"当解析失败的判据**。`_decode` 返回三元组 `(信封有效, 是否新鲜, 值)` 而不是两元组——因为 **None 本身是合法的缓存值**（F-1 的 `(hit, value)` 元组就是为这个设计的，而 F-3 防穿透靠的正是缓存空结果）。拿 None 当解析失败，缓存住的空结果每次都会被当成脏数据去回源，等于把 F-3 废掉一半。
  - 顺带踩到 asyncio 的老坑：`create_task` 的返回值必须留强引用，否则任务可能在跑完前被 GC 掉（官方文档明确警告过）。存进一个 set，完成时用 `add_done_callback` 丢掉。
- **解决**：`app/core/cache.py`。`KEY_PREFIX` 从 v1 升到 v2——值的结构变了就必须换前缀，否则新代码会把 v1 的裸值当信封解析。**这正是 F-1 当初留这个前缀的用处，第一次真的用上了。** `_rebuilding` set 给重建去重（少了它，要防的回源洪峰会原样出现在后台，只是不再挡着请求）。`exp` 用 `time.time()` 墙上时钟而不是 `monotonic()`：这个值要被其他进程读出来比较，monotonic 的零点每进程不同，跨进程比毫无意义；机器间时钟偏移在这里只让刷新时刻早晚偏几秒，无害——和 C06 心跳判活不同，那里偏移会直接变成误判，所以必须用 Redis 单一时钟。指标加 `cache_reads{level="l2", result="stale"}`。
- **验收**：13 项单测。核心那条判的是**耗时**不是返回值：loader 睡 200ms，断言整次读 <100ms——如果等了回源，耗时必然 ≥200ms。过期的信封直接构造（`exp` 减去一个数）而不是等自然过期：等 300 秒的测试没人会跑，而"过期"在这套设计里就是那个字段的一个数字，构造它不失真。全量 149 项全绿。
- **经验**：
  - 缓存三件事（穿透 / 击穿 / 雪崩）的解法是**三种不同性质的东西**，不能互相替代：穿透靠在门口拦（布隆），击穿靠让并发共享一次回源（singleflight），雪崩靠把回源从请求路径上摘下来 + 打散到期时刻。F-3 到 F-5 是叠加而不是递进。
  - **给缓存值套信封之前，先想清楚"版本前缀该不该动"**。改值的结构而不换 key 前缀，灰度期间就是一半请求解析失败。
  - 顺手加的优化会打断后加的机制：F-4 那个二次检查 L1 在当时完全正确，到 F-5 就成了 bug。**每加一层缓存路径，都要回头检查已有的短路判断在新路径上是否还成立。**
  - 逻辑过期额外白拿一层韧性：数据源短暂不可用时，"当场回源"的写法会让读接口一起失败，而这里只是继续供旧值、下一个读的人再派一次重建。

## 2026-08-12 · F-4（singleflight 防击穿）

### 029 singleflight 要用 future 而不是锁；难的不是互斥，是取消传播和二次检查

- **现象/起因**：F-1 到 F-3 之后还剩一个洞。一个热 key 恰好过期（或被 F-2 失效）的那一瞬间，所有正在读它的请求同时发现未命中，于是**同时**回源——缓存平时挡住的那些 QPS，在这一刻原封不动砸到 MySQL 上。**key 越热砸得越狠：热点是它的前提，不是缓解因素。** 和穿透的区别很清楚：穿透查的是根本不存在的东西，布隆能在门口拦掉；击穿查的是真实存在且很热的东西，拦不得也拦不掉，只能让它们**共享一次回源**。
- **选型：future 而不是锁**。第一版想法是给 key 加 `asyncio.Lock`，但锁只解决"不同时查"，不解决"不重复查"——后来者拿到锁之后还是会各自再查一次库（除非在锁内重查缓存，那又要求回填必须先完成）。用 future 是直接把"第一次的结果"交给所有等待者：N 个并发 → 1 次查询 + N-1 次等待。**目标是少查，不是排队查。**
- **根因（真正的坑，两个）**：
  - **取消传播会放大故障**。直接 `await` 共享 future 时，任何一个等待者的 task 被取消（客户端断开就会），取消会顺着传到共享 future 上，把**正在回源的那个人和其他所有等待者一起打断**。本来是收敛故障的机制，反而变成"一个客户端断开就能弄失败一片请求"。解法是 `asyncio.shield`，让取消只作用于当前等待者。反过来也要处理：回源方被取消时必须把等待者放掉，否则它们永远挂在一个不会完成的 future 上。这里要捕获 `BaseException` 而不是 `Exception`——`CancelledError` 从 3.8 起不是 `Exception` 的子类，只 catch `Exception` 会漏掉它，而漏掉的后果正是"永久挂死"。
  - **必须在占位前二次检查 L1**。调用方查 L1 未命中之后，还 `await` 过一次 L2 读；那期间足够别的任务完整跑完一次回源并回填。尤其 loader 是同步 ORM 查询时，它从头到尾不让出事件循环，等这个任务被调度回来，"正在回源"的痕迹已经没了——不重查 L1 就白查一次库。**并发正确性的判断依据是"两次 await 之间世界会变"，不是"代码看起来是顺序的"。**
  - 失败路径必须清 `_inflight`。留着不是"多查一次"而是**永久故障**：后来的请求会挂到一个已完成且带异常的 future 上，这个 key 从此再也回源不成功。
- **解决**：`app/core/cache.py` 的 `_load_once`。`_inflight` 是 `key → future`，互斥按 key 而不是全局（全局锁会把不相关的回源串起来，等于自造吞吐瓶颈，而且它每次未命中都在生效，比击穿更糟）。只有回源者写缓存，等待者不写（否则是 N-1 次重复写）；回填放在结果交付之后，等待者不必等两级缓存写完。指标加了 `cache_reads{level="singleflight"}`，它和 `db` 档的比值就是防击穿的收益。**边界写清楚了：这是进程内互斥，不是集群级的**——M 个进程各自回源一次，最坏 M 次不是 1 次。没上分布式锁是代价不对等：分布式锁要在每次未命中路径上多付一次 Redis 往返，还引入新故障模式（持锁者崩了别人等锁超时，超时设短又退化成没锁），而 M（进程数，个位数）远小于 N（并发请求数）。**把 N 压到 1 是数量级改善，把 M 压到 1 是常数级改善，代价却高得多。**
- **验收**：10 项单测，`asyncio.gather` 起 50 个并发断言 `loader.calls == 1`。**没用压测**：击穿是并发时序问题不是吞吐问题，协程能精确复现"同时未命中"这个瞬间，比压测可靠也快得多。测试里 loader 刻意是 `async` 且真 `await`——同步 loader 不让出事件循环，测出来的"1 次回源"是串行执行的假象，不是 singleflight 的功劳。全量 136 项全绿。
- **经验**：
  - 共享 future 的并发原语，**危险都在异常和取消这两条路径上**，不在正常路径。正常路径一眼就对，取消传播的方向要一个个想清楚：等待者取消不该影响回源方，回源方取消必须释放等待者。
  - `asyncio.CancelledError` 不是 `Exception`。凡是"必须保证清理"的 `try/except` 都要意识到这一点，只 catch `Exception` 的清理代码在取消面前是失效的。
  - 用"每次未命中要额外付多少"来判断一个防护机制值不值：singleflight 在未命中路径上零额外 IO，分布式锁要多一次往返。**防护机制本身的成本落在哪条路径上，比它的效果更能决定该不该做。**

## 2026-08-12 · F-3（布隆过滤器防穿透）

### 027 布隆过滤器能当门卫，全靠它的误判是单向的；而"无假阴性"是登记齐全的性质，不是算法的性质

- **现象/起因**：F-1 已经缓存空结果，同一个不存在的 `game_id` 只会穿一次。但攻击者每次换随机 id，每个 id 都是全新的 key、都要穿到 MySQL——**缓存等于不存在**。这就是穿透：不是缓存失效，而是被查的东西压根没进过缓存（和击穿"热 key 刚过期"、雪崩"大批 key 同时过期"是三件不同的事）。
- **排查/选型**：能拦在回源之前的东西必须满足一个条件——**它说"不存在"时必须是对的**。布隆过滤器刚好如此：可能误判"存在"，绝不可能误判"不存在"。所以"不存在"→直接 404，"存在"→可能是误判，照常往下走缓存和数据源。**如果误判方向反过来（可能漏报存在），它一点用都没有**，会把真实房间判死。128 KB 位图（m=2^20、k=7）换掉全部无效回源，而误判"存在"的后果只是"这次没拦住"，多查一次库。
- **根因（真正的坑）**：算法只保证"加进去的一定查得到"，**没加进去的它一样答"不存在"，而这时的"不存在"是错的**。两种情况会踩到：① 过滤器上线之前建的老房间从没登记过；② Redis 被清过、位图归零。这两种情况下拦请求就是把真实房间判死。所以：位图为空时一律放行、key **不设 TTL**（过期归零和被清空是同一种事故）、启动时若位图不存在则把库里已有 id 灌一遍（`bloom.warm`）。这三条不是优化，是正确性的前提。判错的两个方向完全不对等——**少拦一个不存在的 id 只是多一次查询，错拦一个真实房间是功能直接坏掉**，和 E-1"不按存活视图过滤广播目标"（记录 020）是同一条推理。
- **解决**：`app/core/bloom.py`。哈希用 `hashlib.md5` 不用内置 `hash()`——同 C05 那个坑，`PYTHONHASHSEED` 随机化让内置 `hash()` 每个进程结果不同，而位图是跨进程共享的，各进程算出不同的位就完全失效（单测起了个子进程算一遍来钉住这条）。双哈希法从一个 16 字节摘要切出 h1、h2，第 i 位取 `(h1 + i*h2) & BIT_MASK`；h2 强制成奇数，避免与 2 的幂有公因子导致 k 个位置塌缩成一个。登记点在 `create_game` **持久化成功之后**（建局失败的不该登记）；拦截点在 `GET /{game_id}` 和 `GET /{game_id}/events` 两个 HTTP 入口，且放在**跨节点转发之前**——不存在的 id 本来要先跳一次再由目标节点答 404，在这里拦掉连这一跳都省了。刻意**不**拦 `load_game` 本身：AI 任务和快照恢复都走它，那是内部调用，id 必然来自已存在的房间。所有 Redis 读写失败一律放行——**过滤器是加速机制，不是可用性依赖**。指标 `bloom_rejects` 就是"省下的无效回源次数"。15 项单测，一半在验证异常情况下它会放行而不是拦截。线上实测：清空位图后重启，预热登记 611 个已有房间，`strlen` 131038 字节、`ttl` -1。
- **经验**：
  - 概率型数据结构的可用性，取决于**它的错误方向和业务的容错方向是否对齐**。布隆能当门卫不是因为它省内存，是因为它只会错向"放宽"。选型时先问"它错的时候错在哪边"。
  - 一个机制的保证边界，往往不在算法里而在**数据的完整性**里。"无假阴性"是数学结论，但前提是"所有存在的都登记了"——这个前提由预热、不设 TTL、空位图放行三条工程约定维持，少一条整个结论就作废。
  - 拦截点越靠前越值：放在转发之前比放在业务查询之前多省一次跨节点往返。

## 2026-08-11 · F-2（事件驱动失效 + TTL 兜底）

### 026 失效要对齐"数据源的可见时刻"，不是业务动作的发生时刻

- **补的是 F-1 留下的洞**：L2 是共享的，删一次全集群立刻看到；L1 在每个进程自己的堆里，别的进程改了数据它毫不知情，会一直供旧值到自己 TTL 到。补法是一条 Pub/Sub 失效通道：谁失效了 key 就喊一声，所有进程听见清自己的 L1。
- **最容易写错的是时机，不是机制**。这份缓存回源的是 MySQL，而事件走 Write-Behind——动作发生时事件只进了 Redis Stream，MySQL 里还没有。**如果在动作发生时失效，紧随其后的读会回源到一个还没刷进新事件的 MySQL，然后把这份旧结果重新缓存 300 秒**。比不失效更糟：不失效至少是"旧值"，提前失效是"把旧值重新盖章成新值"。所以失效点挂在 flusher 的 `commit` 之后，而不是 `process_action` 里。**失效要对齐数据源的可见时刻。**
- **失效在游标推进之前**：崩溃会导致重刷 + 重失效，两者都是幂等的，宁可重来。
- **这次刻意用全集群广播，和 E-1 的 WS 扇出刻意不广播正好相反**。区别在于有没有办法知道该发给谁：WS 有连接路由表，能查出"这个房间的连接在哪几个节点"；而"哪个进程的 L1 里存着这个 key"没有任何登记，每个进程都可能有，只能广播。**能定向的时候定向，定不了的时候才广播。**
- **也不需要防环**：E-1 那里收到转发必须防止再次扇出（否则 A→B→A 死循环），这里收到消息只是删本地一个 key，删自己已删过的 key 是幂等的，连自己收到自己的消息都无所谓。**幂等的操作不需要防环——这是能省掉一整层机制的原因。**
- **发起方要同步清自己的 L1，不能等广播绕回来**：Pub/Sub 是 fire-and-forget，绕一圈至少一次往返，这期间本进程仍在供旧值，而它明明是知情的那一方。
- **按 game_id 去重**：一批 500 条事件可能只涉及几个房间，逐条发就是几百次无用广播。
- **失效失败一律不上抛**：数据已经落库，失效发不出去最坏是多留一个 L1 TTL 的旧值——**这正是 L1 短 TTL 作为兜底存在的意义：失效机制是优化，TTL 才是保证**。所以刷库不能因为失效失败而回滚。
- **测"顺序"用源码顺序断言**：真跑一遍 flush 要 MySQL + 完整环境，而这里要钉的恰恰是两个调用的先后，顺序本身就是被测对象（`test_invalidation_happens_after_the_db_commit`）。
- **关联代码**：`cache.py` 的 `INVALIDATE_CHANNEL` / `_subscribe_loop` / `invalidate_events`，`event_flusher.flush_once` 刷库后失效，`main.py` 生命周期接入，测试 9 项，全套 111 项绿

## 2026-08-11 · F-1（L1 + L2 两级缓存）

### 025 缓存该加在哪条读路径上：像缓存的那条其实是权威状态，不能碰

- **最先要判断的不是怎么写，而是加在哪**。全站看着最该缓存的是"读对局状态"，但那条路（`load_game`）加不了：归属节点的 `games` 字典是 Actor 的**权威状态**（单写者），不是缓存；而非归属节点刻意不留副本，否则房间迁过来会照旧副本继续演进，造成对局回退（DEVLOG 018）。**往那条路加缓存等于把 018 那个 bug 重新引进来。**
- **真正该缓存的是回放事件流**（`GET /{game_id}/events`）：它是全站唯一每次都真的回源 MySQL 的读接口，而且事件是**追加写**的、只增不改，缓存起来没有一致性负担。判据是"这份数据改不改"，不是"这个接口热不热"。
- **L1 存在的意义不是"更快一点"**：L2 命中已经省掉了 MySQL 查询，但还要付一次网络往返 + 一次 JSON 反序列化；L1 存的是**已反序列化好的对象**，命中时两笔都不付。省的是网络**和** CPU。
- **L1 的 TTL 就是它的一致性上限**：Redis 是共享的，删一次全集群立刻看到；L1 在各进程自己的堆里，别的节点改了数据这个进程根本不知道。所以 L1 取 3s、L2 取 300s，**理由不是"3s 比较快"，而是 3 秒脏读能接受、300 秒不行**。已写测试把这个行为钉住（`test_l1_ttl_bounds_cross_process_staleness`），它不是 bug 是固有代价。
- **两级缓存里必须躺同一种形状**：ORM 对象直接塞进 L1、JSON 塞进 L2，会导致命中 L1 拿到 ORM 对象、命中 L2 拿到 dict，**行为随命中哪一级而变**——这种 bug 只在缓存刚过期那一瞬间出现，极难复现。所以进缓存前先统一转成可 JSON 化的 dict（`_events_to_dicts`）。附带好处：ORM 对象绑着 Session，Session 关掉后访问懒加载字段会直接抛异常。
- **未命中不能用返回 None 表示**：`get` 返回 `(是否命中, 值)` 元组。因为缓存里本来就可能存着 `None`——空结果缓存是 F-3 防穿透要用的，用 None 表示未命中会让空结果每次都判未命中、每次都回源，防的那个穿透原封不动。
- **L1 必须有条数上限**：key 里带 `game_id` 这种无界维度，不淘汰就是内存泄漏（开一局多一条，永不释放）。淘汰先清过期的，都没过期才按插入序丢最旧（dict 保序）；没上 LRU 是因为热点会被反复访问不断续期，FIFO 足够，上 LRU 要在热路径上多维护一条链表。
- **缓存是加速手段不是可用性依赖**：L2 读写失败一律记日志后穿透到数据源，Redis 故障时读接口应该变慢而不是报错。
- **key 带版本前缀** `aivalon:cache:v1`：改了缓存值结构时 bump 前缀让旧值整体作废，否则灰度期间表现为"一半请求缺字段"。
- **关联代码**：`app/core/cache.py`、`game_service.get_game_events_cached`、`routers/game.py` 事件流端点、`metrics.cache_reads`（level=l1/l2/db 的命中计数就是验收口径），测试 13 项，全套 102 项绿

## 2026-08-11 · E-5（WS 网关拆成独立服务）

### 024 拆网关的实质是"哪些 router 挂在这个进程上"，而拆分能被一行 import 抵消

- **为什么要拆**：长连接和业务代码的生命周期天生不一致。业务代码要频繁改、改完就得重启，而重启一个持有 2,000 条长连接的进程，代价是这 2,000 个客户端同时掉线重连——同居一个进程等于让"发一次版本"和"全员掉线"绑死。拆开后业务节点随便重启，连接不受影响（广播照样通过 Redis 路由表投递进来）。另一半好处是扩容维度不同：连接吃内存和文件描述符，业务吃 CPU 和 DB 连接，各自独立扩容比一起扩省。
- **怎么拆**：新增 `app/gateway.py` 作为独立入口，**复用 `ws.router` 本体**，只挂这一个路由，不挂 auth/games/users。刻意不复制一份 WS 代码：复制的写法会让两边慢慢长歪，最后"网关行为和主进程不一致"变成排障噩梦。
- **关键约束——网关不进一致性哈希环**：网关需要一个身份（要有专属广播频道、要能登记进房间路由表），但绝不能出现在 `node_registry` 的 `NODE_SET_KEY` 里，那个 ZSET 是哈希环的唯一数据源。网关进环，就有 1/N 的房间被分配给一个没有业务逻辑、没有 Actor 的进程，转发过去的动作无人处理。**身份和"是否参与房间归属"本来是两件事**，网关只要前者，落地就是不调 `node_registry.init()`。
- **`GATEWAY_ID` 与 `NODE_ID` 必须分开**：同机部署若共用一个 id，两个进程会抢同一个专属频道，且都以为自己持有该房间的连接。
- **最值得记的一点**：拆分完成后回头看 `routers/ws.py`，它 `import GameService` 只为了判定推送等级——**这一行就把 ORM 模型、规则引擎、Celery 全拉进了那个只该拿着 socket 的进程**，网关会因为业务层的任何 import 错误起不来、跟着业务发版一起重启，拆分的全部收益被一行 import 抵消。抽出 `core/ws_tier.py`：把 Redis 快照当只读数据，`json.loads` 抠出座位表，不反序列化成 `GameState`（那又牵回业务依赖）。**进程边界不是看目录结构，是看依赖图。**
- **职责边界要用测试钉住**：约定会在某次"就加一行 import"里悄悄失效。用 AST 取真实 import 列表来断言，**不 grep 源码文本**——注释和文档字符串里会正常提到这些模块名，grep 会把说明当违规（第一版就这么误报了两条）；也不查 `sys.modules`，主进程里业务模块早被别处导入过，分辨不出是谁导的。
- **降级方向**：快照读不到 / 是坏数据 / Redis 不可用，一律按旁观者接入而不是拒连。宁可把玩家误判成旁观者（只慢半秒），也不要因为一次读失败把人挡在门外。
- **关联代码**：`app/gateway.py`、`app/core/ws_tier.py`、`routers/ws.py` 去业务依赖、`config.py` 的 `GATEWAY_ID`，测试 9 项（`tests/test_ws_gateway.py`），全套 90 项绿

## 2026-08-11 · E-4（分级推送）

### 023 分级推送：分的是"节奏"不是"权限"，以及角色判据不能让客户端自己说

- **做了什么**：一条消息按接收方分三档下发——操作者单播 / 房间成员即时广播（50ms 合并窗口）/ 旁观者聚合批量（500ms 窗口打成一个 `BATCH` 帧）。
- **分级分的是什么**：`Tier` 决定的是**收帧节奏**，与"能看到什么"无关。看得到什么是脱敏的事（`get_player_view` 已有），两者不能混在一个概念里——否则以后想让某类玩家慢收就得动脱敏逻辑。
- **旁观者窗口取 500ms 的理由**：比玩家的 50ms 大一个量级。旁观者不参与决策，晚半秒看到与即时看到体验上没区别，而帧数能压下一个数量级。**能放松到什么程度取决于这类接收方的时效需求，不取决于技术上能做到多快。**
- **聚合缓冲超上限丢最旧**（`SPECTATOR_BATCH_MAX = 64`）：旁观者要的是跟上进度，不是逐帧回放。这和 022 断开慢消费者是同一条逻辑——积压的旧帧没有价值。
- **角色判据必须服务端定**：用"这个 user 在 `game.players` 里有没有座位"判定，**不接受客户端自己声明角色**。否则任何人都能声明成玩家，把本该聚合的流量提成即时流量，分级就白做了。查不到房间时按旁观者接进来（可能刚建局还没落地），不挡连接。
- **单播也要走跨节点通道**：操作者的连接不一定在处理动作的那个节点上（同 E-1 的漏洞），所以照样查路由表定向投递，消息到目标节点后再按 `user_id` 筛出那一条连接。线格式因此从 `game_id\nmsg` 扩成 `game_id\n单播目标\nmsg`——用行分隔而不是再套一层 JSON，因为 `msg_json` 本身已是 JSON，套壳等于每跳多一次解析和转义。
- **单播不进合并窗口**："轮到你操作了"这种消息合并掉就是丢信息，判据同 021 的白名单。
- **关联代码**：`socket_manager.py` 的 `Tier` / `_Conn.add_to_batch` / `flush_batch` / `unicast`，`routers/ws.py` 握手定级，`protocol.py` 新增 `BATCH` 操作码，测试 5 项

## 2026-08-11 · E-3（慢消费者背压）

### 022 "缓冲满了就断开"会把健康连接全杀掉：满不满要看能不能排空，不是看某一瞬间

- **原有问题**：`_send_local` 在广播循环里逐个 `await ws.send_text()`。客户端不读数据时 TCP 窗口填满，那个 await 永久挂住，**整个房间的广播卡在这一个慢客户端上**（队头阻塞）。一个手机切后台的玩家能让全桌 8 个人都收不到更新。
- **改法**：每条连接自带一个 `asyncio.Queue(maxsize=32)` 和一个写协程。广播只往队列里塞，真正发送由写协程做，广播路径再也不 await socket。
- **踩坑（这次最值得记的）**：判定"缓冲满 → 慢消费者 → 断开"用 `put_nowait` 的 `QueueFull` 做判据，结果**健康连接被全部误杀**（测试里 96 帧全灭）。根因：广播循环里连续塞几十帧，中间没有任何真正的挂起点，写协程从未被调度过，缓冲当然是满的。**某一瞬间缓冲是满的，不代表消费者慢——只代表还没轮到它排水。**
- **解决**：满了先 `await asyncio.sleep(0)` 让出一次事件循环，再试一次入队。消费者健康的话这一让就把队列抽空了；卡死的话写协程正挂在 `send` 上，让也没用，第二次仍失败才判死。`sleep(0)` 只等一个 tick、不依赖任何 socket，不会把队头阻塞放回来。
- **第二个坑**：`stop()` 里 flush 完挂起帧就 cancel 写协程，等于白 flush——flush 只是塞进缓冲，发出去是写协程的事。加 `_drain_all(timeout=1.0)` 先排空。**超时必须有**：慢消费者的队列永远排不空，无限等会把进程退出流程挂死。
- **断开而不是限速的理由**：积压的帧本身已经是过期状态，客户端永远追不上。断开让它重连后一次拉到最新状态，比慢慢补一堆旧帧更快也更省。关闭码用 1013 Try Again Later，语义就是"可以重连"。
- **`_drop` 里的关闭也要异步**：慢消费者的 socket 本来就写不动，`await conn.ws.close()` 等于把广播路径重新卡回去，那背压就白做了。丢进后台 Task。
- **经验**：
  - **凡是"看当前值判定状态"的逻辑，先问这个值有没有被观测时机污染**。这次和 019（分位数样本量）是同一类错误的两个面：019 是样本太少不足以代表分布，这次是采样时刻系统还没运行到能反映真实状态。判据都得是"给它公平机会之后仍然如此"。
  - 广播路径上**任何** await socket 的操作都是队头阻塞源，包括看起来无害的 `close()`。
  - 接口契约变了要说清：改造后 `broadcast()` 返回不再意味着"已写进 socket"，两个老测试因此需要加等待——不是测试写错了，是契约真的变了。
- **关联代码**：`socket_manager.py` 的 `_Conn` 类 / `_send_local` / `_drop` / `_drain_all`，指标 `ws_slow_consumers_dropped`，测试 5 项

## 2026-08-11 · E-2（同 Tick 事件合并帧）

### 021 合并帧的前提是"丢掉中间帧不丢信息"，以及两个顺序坑

- **背景**：一次人类动作会触发 AI 连锁推进，短时间内产生多个状态更新，每个都广播一遍等于白烧带宽。合并窗口内只下发最后一帧。
- **合并的合法性条件（最关键的一点）**：`STATE_UPDATE` 的 payload 只是"去拉最新状态"的通知，**同一房间连发 N 帧与发 1 帧对客户端完全等价**，所以中间帧可以安全丢掉。`AI_THINKING` 带 player_id、`ERROR` 带原因，合并就是丢信息。所以合并白名单是 `COALESCIBLE = {STATE_UPDATE}`，不是"所有消息都压一压"。**能不能合并是消息语义决定的，不是性能决定的。**
- **"同 Tick"落地成什么**：项目里没有全局 tick 循环，动作是事件驱动的，所以"同 Tick"实现为一个 `TICK_INTERVAL = 50ms` 的合并窗口。取 50ms 是因为人眼分辨不出，而一次动作触发的 AI 连锁刚好落在这个量级。
- **顺序坑一：立即帧不能越过挂起帧**。不可合并的帧要立即发，但若直接发就会越过窗口里挂着的 `STATE_UPDATE`——客户端先收到"AI 正在思考"，再收到上一次的状态更新，顺序反了。解法是发立即帧之前先 `_flush` 掉挂起帧。
- **顺序坑二：定时器要先注销再 flush**。写成"先 flush 后注销"的话，flush 里有 await，期间新来的帧看到 `_tick_tasks` 还占着就不开新窗口，那一帧会挂在 `_pending` 里等不到任何定时器来发它——表现是"最后一次状态更新永远不下发"，而且只在高频动作下偶发。
- **收摊要 flush**：`stop()` 里挂起帧先发掉再退出。最多只欠一个窗口的量，丢掉等于让客户端停在一个过期状态上。
- **验收口径**：`ws_frames_sent` / `ws_frames_merged` 两个 Counter 相比即合并率。合并在**源头**做，所以跨节点也只发一帧——省的是网络，不只是客户端带宽。
- **关联代码**：`socket_manager.py` 的 `_enqueue` / `_tick` / `_flush` / `_dispatch`，测试 6 项

- **经验**：

  - 测试里的"破坏性操作"要问清爆炸半径。`CLIENT KILL TYPE pubsub` 这种服务端全局操作，在共享 Redis 上会打到测试范围之外。

## 2026-08-11 · D-3.5（动作 P99 口径复测：一个写进简历的数字站不住）

### 019 "动作 P99 < 100ms"两轮实测差三倍：不是性能不稳，是分位数口径错了

- **现象**：核对简历数字出处时，翻 DEVLOG 012 修复后那两轮干净复测（`s2_u20_fix_r1/r2`，共 9536 请求零失败），发现同一条简历描述在两轮里结论相反：
  | 动作 | r1 P99 | r2 P99 |
  |---|---|---|
  | speak | 47ms | **130ms** |
  | mission | 43ms | 95ms |
  | vote | 46ms | 53ms |
  同机器、同并发、同脚本、都零失败，P99 差近三倍。按"< 100ms"这个口径，r1 达标 r2 不达标
- **排查**：先怀疑是系统抖动（后台刷库、GC、Celery 争 CPU），但这个方向不对——如果是抖动，四类动作应该一起变差，而 vote 几乎没动。改去数样本量，问题立刻显形：一轮 120s 里 `speak` 约 200 个请求、`propose` 只有 20 来个。**P99 落在第 2~3 慢的那几个样本上**，等于在拿单个离群值当指标。再看 locust 的分位数实现，第二个问题也在：它按响应时间分桶归整后计数再插值（同 C03 讲 Histogram 那套），不是原始值排序
- **根因**：**两个测量口径缺陷叠加，不是系统性能问题**。① 分动作切分后每格样本量不足百量级，P99 的定义要求"第 99% 名"，n=200 时它就是第 2 名，噪声直接变成结论；② locust CSV 的分位数是分桶估算值，够看趋势不够写简历。真实分布其实很稳——两轮里超过 100ms 的动作各只有 2 个（0.6% / 1.0%）
- **解决**：给 `bench/locust_s2.py` 挂 `events.request` 监听器采原始延迟（只收成功请求：失败请求的耗时是超时值，混进延迟分位数没有意义），`events.quitting` 时落 JSON 存档并打印精确分位数（最近秩法，不插值）。关键一步是**把所有 `POST /action *` 汇成一个池子**——样本量上千，分位数才有意义。然后当前机器重跑两轮：

  | 口径 | r1 | r2 | 两轮合并 |
  |---|---|---|---|
  | 动作类合计样本 | 322 | 200 | 522 |
  | P50 | 17.9ms | 18.2ms | 18.1ms |
  | P95 | 49.1ms | 59.3ms | 52.2ms |
  | **P99** | **82.8ms** | **83.8ms** | **83.8ms** |
  | max | 148.6ms | 281.0ms | 281.0ms |
  | 失败 | 0 / 4460 | 0 / 4343 | 0 |

  合池后两轮 P99 差 1ms——**这才是可以写进简历的数字**。简历①的"动作 P99 < 100ms"成立，但口径必须补一句"动作类接口合计"
- **顺带发现一个同类问题（简历③）**：简历写"创建对局耗时从 30s 池等待超时降至 226ms"，而 226ms 是当初单轮的 **max**。这两轮的创建对局 max 是 187ms 和 411ms——**max 是所有统计量里最不稳的一个**（它就是"最差的那一个样本"，n 越大越容易更大）。改简历时把口径从 max 移到 P99（两轮合并 411ms、P50 154ms），或者只讲"从 30s 超时到亚秒级"这个量级差
- **经验**：① **分位数是样本量的函数**。报 P99 必须同时报 n——n=200 的 P99 是第 2 名，n=2000 的 P99 才是真的第 99%。切分维度越细，每格样本越少，分位数越接近噪声。压测里"按接口分开看"是排障视角，"合池看"才是容量视角，写简历用后者；② **max 不适合做简历数字**，它没有统计稳定性，同样条件下换一轮就能翻倍。要讲改善量级就讲 P99 或 P50；③ **"两轮一致"这条规矩这次真救了一回**（规矩来自 015 的写压力对比）。如果当初只跑 r1 就把 47ms 写进去，现在就是个随时复现不出来的雷。反过来说，**两轮不一致时先怀疑测量口径，再怀疑系统**——这次系统一直是稳的，错的是尺子；④ 工具给的分位数要知道它怎么算的。locust 和 Prometheus Histogram 都是分桶估算，够用但有前提；要写进对外材料就自己存原始值算，而且**原始值必须留档**（存了 `*_latency_raw.json`），否则事后想换口径就得重跑压测
- **关联代码**：`bench/locust_s2.py` 头部的原始延迟采集器；`bench/results/s2_u20_p99_r1/r2_latency_raw.json`（原始样本）；概念见 C07

## 2026-08-11 · D-3（房间路由接入请求路径 + 双节点演练）

### 016 转发头白名单漏一个鉴权头：表现是"该端点固定 403，对局静默卡死"

- **现象**：双节点演练第一次跑，转发验证阶段人类玩家 **6 个动作一个都没提交成功**，而且**没有任何一条拒绝日志**——脚本只是反复轮询状态、始终判断"没轮到我"，最后超时退出
- **排查**：因为没有报错，先怀疑是判定逻辑抄错了。改去看两个节点的 access 日志，发现 node-2 上一串 `POST /ai_action -> 403`，node-1 上对应的是 `httpx: POST http://127.0.0.1:8002/.../ai_action "HTTP/1.1 403 Forbidden"`——转发这一跳本身是通的，是**被转发到的节点拒绝了鉴权**
- **根因**：`room_router.forward()` 对请求头做了白名单裁剪，只透传 `authorization / x-idempotency-key / x-request-id`。但 AI worker 的内部接口 `ai_action` 用的是**另一个**鉴权头 `x-internal-secret`，转发时被丢掉 → 归属节点判定内部密钥不匹配 → 403。AI 玩家全部动不了 → 对局永远停在 AI 的回合 → 人类玩家永远等不到自己的回合。**人类侧 0 提交只是症状，病灶在 AI 侧**
- **解决**：把 `x-internal-secret` 加进白名单，并在 `forward()` 的 docstring 里写明"新增带自定义鉴权头的端点时必须同步加进来"。补 `test_forward_passes_through_critical_headers` 断言这四个头逐一透传
- **经验**：
  - **白名单转发的固有维护成本**：漏一个头不会报错，只会让某条端点在转发后固定失败。反过来若用黑名单（除了 Host/Content-Length 全透传）就不会漏，但会把不该跨节点传的头也带过去。选白名单就得接受"每加一个自定义头都要回来改这里"，所以必须把这条约束写在代码注释里，而不是指望下次记得
  - **调试时别被症状的位置误导**：失败发生在人类玩家的提交路径，根因在 AI 的提交路径。多节点系统里"谁没动"和"谁坏了"经常不是同一个组件
  - 这个 bug 单机永远不可见——单机不转发，头就永远不会丢

### 017 只给写路径接路由是不够的：读路径会读到一份永不更新的死副本

- **现象**：修完 403 后，AI 动作全部 200，人类玩家**依然 0 提交**，依然没有任何拒绝日志
- **排查**：直接查那局的实际状态，发现从 node-1 读到的快照 `phase/round` 一直不动，而 node-2 上的 Actor 明明在推进。顺着 `get_game_state` 往下看到 `GameService.get_game(game_id)` → `return games.get(game_id)`——读的是**进程本地字典**
- **根因**：这一步只把 `submit_action` / `ai_action` 两条**写路径**接进了路由，读路径没接。建局发生在 node-1，`create_game` 无条件写下 `games[game_id] = initial_state`；房间归 node-2，动作全部被转发到 node-2 执行。于是 **node-1 手里留着一份建局那一刻的初始状态副本，且永不更新**。演练脚本从 node-1 轮询，看到的永远是第 1 轮发言阶段，`decide()` 自然永远算出"没轮到我"
- **解决**：`get_game_state` 加上同样的 `should_forward` / `forward`。转发的代价是集群内多一跳，换来"读到的一定是刚写进去的那份"
- **经验**：
  - **有状态服务的路由必须覆盖读写两侧**。无状态服务里读请求打到哪台都一样，这个直觉在单写者模型下是错的：状态在特定进程的内存里，读错节点就是读到过期数据。**"只路由写"是个看起来合理、实际半残的方案**
  - 又一个"没有报错的 bug"。返回 200、数据结构完整、字段合法，只是**内容是旧的**。这类问题不会被状态码监控发现，得靠业务不变量（比如"轮次只能前进"）才能兜住
  - 判据要选能证伪的：演练里用"房间只驻留在归属节点的 `resident_games` 里、入口节点为空"做断言，比看响应码有力得多

### 018 非归属节点留下的内存副本，会在房间迁回来时让对局回退

- **现象**：宕机迁移演练一开始就 `404 Not Found`——从幸存节点读那个归属别人的房间读不到
- **排查**：`get_game` 只读本地字典，没有快照兜底。房间归 node-2，但 node-2 **在收到第一个动作前从未把它载入内存**（建局发生在 node-1），转发过去自然 404。前一个演练能过纯属时序运气：AI 动作先到 node-2，替它把状态恢复了
- **根因**：内存副本的信任规则在多节点下失效了，两个方向都错：
  1. **归属节点可能还没有副本** → 读路径必须能回落 Redis 快照
  2. **非归属节点可能留着一份陈旧副本** → `create_game` 无条件写 `games[game_id]`，而建局节点不一定是归属节点。这份副本埋着一颗更深的雷：等房间日后迁到它名下，`process_action` 会因为"内存已有"而**跳过快照恢复**，照着建局那一刻的旧状态继续演进 → 对局回退，且回退得毫无痕迹
- **解决**：
  - 新增 `GameService.load_game()`：本地内存优先，未命中回落 Redis 快照；读路径改用它。**刻意不把回落结果写回 `games`**——否则非归属节点又缓存了状态，回到雷区
  - `create_game` 只在 `cluster.is_mine(game_id)` 时才留内存副本；`_trigger_ai_logic` 改成显式接收状态参数，这样不留副本也能正常触发 AI
- **经验**：
  - **"内存里有就用内存"这条捷径的前提是"本进程是唯一写者"**。多节点下前提变成"本进程是**这个房间的**归属节点"，条件严格了，判断也必须跟着变严格。这类隐含前提失效的 bug，比逻辑写错难找得多
  - **缓存兜底和缓存污染是一枚硬币的两面**：读不到就回落快照（兜底）很自然，顺手把结果缓存起来（污染）也很自然，但在非归属节点上后者是有害的。区别只在"这个节点有没有资格持有这份状态"
  - 三次演练三个 bug，全部是"单机跑不出来"的类型，且全部**不报错**。这正是当初决定"第一步只写哈希环的纯算法 + 单测，先不接请求路径"的理由——路由 bug 的特征是不扩容看不见、看见了难定位

### 015 "写压力 -80%"怎么测：先想清楚"压力"是哪个维度，否则测出来是 0%

## 2026-08-11 · D-2 收尾（宕机恢复演练 + RPO 量化）

### 013 宕机恢复演练与 RPO 量化：Write-Behind 的丢失窗口到底有多大

- **要回答的问题**：Write-Behind 把"每动作同步写 MySQL"改成了"先写 Redis、后台每 200ms 批量刷库"，性能是买来的，代价是**引入了一个丢失窗口**。简历写"量化验证宕机恢复 RPO"就必须给出这个窗口的实测值，而不是"理论上很小"
- **先把 RPO 拆成两个维度**（这一步比测量本身重要）：
  - **时间维度**：最坏丢 ≤ 一个刷库间隔 = **~200ms**（`FLUSH_INTERVAL`），这个是设计值，看代码就知道
  - **条数维度**：已入 Redis Stream 但游标尚未推进的事件数——这才是真丢的东西，**必须实测**，因为它取决于负载
- **两类故障要分开演练**（同一个"宕机"在 Write-Behind 下有完全不同的后果）：
  1. **API 进程挂**（本次演练）：Redis 完好 → 状态快照和事件都在 → **零丢失**，对局可继续
  2. **Redis 也挂**：丢的就是上面那个"未刷条数"窗口 → 这才是 RPO 的适用场景
- **演练一：kill -9 API 进程后对局能否续打**
  - 建局打 8 个动作到 `phase=vote round=2`（27 条发言），kill 前 MySQL 57 条事件
  - `kill -9` API 进程（**注意 flusher 跑在 API 进程内，等于同时杀掉了刷库器**），健康检查 `000`，Redis 快照仍在
  - 重启后读取对局：`phase=mission round=2 speech=28`——比 kill 前更靠前一格，因为 kill 瞬间在途的动作已落 Redis
  - 续打 6 个动作到 `phase=finished round=4`，最终 MySQL 101 条事件，**distinct seq = 101，重复行 0**（`INSERT IGNORE` 幂等生效）
- **演练二：RPO 窗口实测**（`drill_kill_recovery.py watch`，20 房间负载下 45s 采样 427 次 @0.1s）

  | 指标 | 实测 |
  |---|---|
  | 峰值未刷事件数（**最坏 RPO**） | **16 条** |
  | P95 | 10 条 |
  | 均值 | 3.45 条 |
  | 非零采样占比 | 361/427（84.5%） |
  | 时间维度 RPO | ≤ ~200ms |

  即：**20 并发房间满载时，Redis 与 API 同时全灭，最多丢 16 条事件 / 200ms 窗口**。无负载时窗口恒为 0（动作节奏慢于刷库节奏，永远追平）——所以这个测量**必须在负载下做**，空跑出来的漂亮 0 是假数据
- **顺带发现**：演练的对账环节（比对 MySQL 事件数 vs max seq）挖出一个静默丢事件的 bug，见 014。**这就是做演练的额外收益——它逼你去对账，对账才会发现平时看不见的东西**
- **经验**：① **RPO 要拆维度报**——只说"200ms"是不完整的，工程上真正关心的是"这 200ms 里积压了多少条"，而这个数只能实测；② **演练要按故障域分开设计**：Write-Behind 下"API 挂"和"Redis 挂"后果完全不同，笼统说"宕机恢复"会把零丢失的场景和有损场景混为一谈；③ **flusher 与 API 同进程是个隐藏耦合**——杀 API 等于同时杀刷库器，未刷数据只能等重启后由新 flusher 从游标续刷（本次验证了续刷正确），但生产上应考虑拆独立进程；④ 演练脚本要留成可重复执行的资产（`bench/drill_kill_recovery.py` 四段式 `play/measure/resume/watch`），一次性手敲的演练等于没做——D-3 节点迁移还要再用一次

### 014 全库 372 局零条 GAME_START：外键 + INSERT IGNORE 把"丢数据"变成了静默

- **现象**：013 的演练对账时发现一处不对——MySQL 本局事件数 101，但 `max(seq)=102`，差 1。查 seq 连续性：`min=2, max=102`，区间内**无缺口**，唯独 seq=1 不存在。而 seq=1 是固定的 `GAME_START` 事件（`game_service.py:116` 写死）。全库扫一遍：372 局对局，`GAME_START` 事件 **0 条**
- **排查**：`SHOW CREATE TABLE game_events` 看到 `CONSTRAINT game_events_ibfk_1 FOREIGN KEY (game_id) REFERENCES games (id)`。再看 `_flush_batch` 的语句顺序：**先**插事件行（`event_flusher.py:49`），**后**补建 `games` 表记录（`:77`）。GAME_START 是一局的第一条事件，它落库时 `games` 里还没有这一行 → 外键校验失败
- **根因**：`INSERT IGNORE` **把外键错误降级成 warning**——行被丢弃，语句返回成功，事务照常提交，日志一片干净。后续 seq≥2 的动作事件因为 `games` 行此时已补建好，全部正常落库，所以现象是"从 seq=2 起完整无缺口"，看起来像 seq 起始偏移而不像丢数据
- **为什么潜伏这么久**：`INSERT IGNORE` 是为"崩溃重刷幂等"引入的（游标提交后推进，崩溃会重刷 → 靠唯一约束去重）。它对 `(game_id, seq)` 唯一冲突的忽略是**故意的**，对外键失败的忽略是**顺带的副作用**——同一个关键字，一个语义想要，一个不想要，无法分开
- **解决**：把 `games` 记录的补建提到事件插入**之前**（同一事务内），依赖行先于依赖者存在。验证：新建一局，MySQL 前 3 条事件为 `(1,'GAME_START'), (2,'speak'), (3,'speak')`，seq 从 1 起；24 项测试全绿
- **经验**：① **幂等写法要审"它还忽略了什么"**——`INSERT IGNORE` 忽略的是一整类错误（唯一冲突、外键失败、类型截断……），只想要其中一种时它就是个太钝的工具。更精确的替代是 `ON DUPLICATE KEY UPDATE`（只针对键冲突）或先查后插；② **同事务内有外键依赖时，插入顺序不是风格问题而是正确性问题**——批量写路径尤其容易踩，因为语句是循环生成的，顺序藏在代码结构里而不是显式表达的；③ **静默失败比报错危险得多**：这个 bug 没有任何日志、没有异常、测试也全绿（集成测试只断言对局能打完，没断言事件完整性），只有主动对账才能发现。**"写成功"和"写进去了"是两件事**；④ **对账是发现静默 bug 的唯一手段**——顺手做的一次 `count(*)` vs `max(seq)` 比对就挖出来了，这类校验值得固化进演练脚本
- **面试点**：① "`INSERT IGNORE` 有什么坑" —— 标准答案就是这个：它忽略的错误远超你的预期；② "怎么发现数据静默丢失" —— 对账 + 不变量校验（序号连续、计数一致），不能指望报错；③ "为什么集成测试没抓住" —— 测试断言的是流程走通，不是数据完整，断言层级不同

## 2026-08-11 · D-2 收尾（30s 超时墙闭环）

### 012 30s 超时墙真凶：不是泄漏是自死锁——一个请求握着连接去要第二个连接

- **现象**：承接 011。修完三处缺陷后仍复现——20 房间 S2 压测，创建对局 66 次 13 次 500（25.76%），P75 及以后整齐卡在 30000ms（池等待超时值）；同时所有动作接口 P50 14~18ms 零失败。011 里"MySQL processlist 全是 Sleep"这条关键证据始终没被解释通
- **排查**：先做取证工具再改代码（011 的教训：假设未证实就改，一轮通过就当修好）。给连接池挂 checkout/checkin 事件监听（`app/core/pool_probe.py`），checkout 时记下 trace_id + 业务调用栈，后台每 2s 报告"持有超 5s 未还"的连接。开着探针复现，三条证据一次到手：
  1. 15 个连接**全部**签出于 `deps.py:46`（`get_current_user` 的 `db.query`），持有 5.9s 不还，池水位 `Checked out: 15 / in pool: 0` 连续 24 秒一动不动
  2. 这 15 个 trace_id 对应的请求全是 `POST /api/v1/games/`，最终 ERR 于 30.1s（池日志与访问日志靠 trace_id 串起来）
  3. 超时点分两处：**12 次**卡在 `game.py:42(_load_user_map)`、**5 次**卡在 `deps.py:46(get_current_user)`，12+5 = 17 = 全部 500 数量，账完全对上
- **根因**：**"持有并等待"自死锁**，不是连接泄漏。`create_game` 这条路径需要**两个**连接：`get_current_user` 用 `Depends(get_db)`（yield 依赖，连接持有到请求结束）拿第一个，下游 `_load_user_map` 用 `SessionLocal()` 拿第二个。20 并发下：15 个请求各抢到 1 个鉴权连接把池占满 → 它们接着都在等第二个连接 → **占着资源的正是在等资源的人**，池永不恢复 → 12 个卡在第二次获取超时；剩下 5 个连第一个都拿不到，卡在鉴权。这解释了 processlist 全 Sleep：那 15 个连接的查询早跑完了，只是被 yield 依赖握着不放
- **讽刺之处**：这个 bug 是 011 的修复引入的。011 为了"连接不跨 await 持有"，把 `create_game` 里原本复用 `db` 的用户名查询抽成独立的 `_load_user_map` + `asyncio.to_thread`——单请求持有连接数从 1 变成 2，修掉跨 await 持有却造出了双重获取
- **解决**：`get_current_user` 不再用 `Depends(get_db)`，改手动短生命周期 Session（查完立即 `close()`）——**与 DEVLOG 006 修 `get_ws_user` 完全同一招**，当时只改了 WS 路径，HTTP 鉴权路径漏了。改前查过风险：`current_user` 在全代码库只被读 `.id`（7 处），无任何 `add/refresh/delete` 回写，Session 关闭后对象 detach 不会触发 `DetachedInstanceError`
- **验证（前后对比，两轮干净复测）**：

  | 指标 | 修复前 | 修复后 r1 | 修复后 r2 |
  |---|---|---|---|
  | 创建对局失败率 | 17/66（25.76%） | **0/64** | **0/58** |
  | 创建 P50 / P75 | 32ms / **30000ms** | 21ms / 220ms | 30ms / 130ms |
  | 创建 max | 30281ms | **226ms** | **160ms** |
  | 全局吞吐 | 29.74 rps | 40.21 rps | 39.44 rps |
  | 探针 POOL LEAK | 15 次 | **0** | **0** |
  | QueuePool 超时 | 17 次 | **0** | **0** |

  两轮共 9536 个请求零失败，全局最慢请求 213ms。吞吐 +35% 是"不再堵车"的副产物
- **经验**：① **连接池的真实并发上限 = 池大小 ÷ 单请求峰值持有连接数**——池 15 不等于能撑 15 并发，这条路径持有 2 就只能撑 7 个多，20 并发必死。审计资源要按"单请求峰值持有量"算，不是按池大小看；② **区分死锁与过载**：过载是慢、压力降下来会自愈；死锁是循环等待、不会自愈。判据就是探针那张图——池水位钉在满值不动 + 持有者全部空闲（processlist Sleep），这不是"忙不过来"的样子。死锁四条件（互斥/持有并等待/不可抢占/循环等待）这里全齐，破解打"持有并等待"最有效；③ **资源类修复要重算全局资源账**：011 的改动局部完全正确（连接不再跨 await），但把单请求持有数从 1 抬到 2，全局更糟。改资源生命周期时必须问一句"改完这条路径峰值持有几个"；④ **同一个 bug 类型要全路径搜一遍**：006 已经在 WS 上修过 yield 依赖持有连接，HTTP 路径同病同因却漏了两个月。修完一处应立刻 grep 同类写法（`Depends(get_db)` 还剩谁在用）；⑤ **先取证再改代码**是这次唯一做对的流程决策——011 的假设（Actor future 悬挂导致永久泄漏）方向完全错了，Actor 全程没参与，且连接不是永久泄漏而是 30s 后随请求崩掉全部归还的周期性僵局。猜不准的时候，造工具比继续猜便宜
- **面试点**：① "池满了调大池能解决吗"——这题的标准反例，死锁下调大只是把死亡阈值从 7 并发抬到 15 并发；② "怎么判断池满是死锁还是过载"——看持有者在干什么，都在跑查询是过载，全部空闲是有人握着不放；③ "同请求内多次取连接怎么办"——复用同一 Session / 缩短前一个连接生命周期 / 拆独立池做舱壁（flusher 已用第三种）

## 2026-08-11 · D-2 收尾（S2 稳定性复测）

### 011 创建对局 90s/30s 超时墙：不是慢，是"等连接"等死的——三个叠加缺陷

- **现象**：S2 20 并发房间复测，创建对局 P50 90000ms 全部挂死、伴随 500；修复后退化版为 P75+ 卡 30s 超时墙。但已创建房间的动作处理始终很快（P50 30~40ms）——"快的很快、死的全死"是典型的**资源等待**而非**算得慢**特征
- **排查**：服务日志两类报错——`QueuePool limit of size 5 overflow 10 reached`（连接池等 30s 放弃）+ 限流器 `Timeout reading from localhost:6379`（Redis 读超时）。沿 traceback 逐层定位出三个叠加缺陷：
- **根因（三个缺陷，缺一不至于雪崩）**：
  1. **连接泄漏（真凶）**：`restore_game_state` 的 `finally` 里用 `if not db` 判断是否关闭自建 Session——但 `db` 在函数开头已被重新赋值，条件恒为假，**每次房间唤醒泄漏 1 个连接**。15 个房间唤醒即永久打满共享池（pool 5+overflow 10），此后所有请求排队 30s 等连接
  2. **事件循环冻结（放大器）**：`get_current_user`、`create_game` 是 `async def` 却直接做同步 `db.query`——等池连接是在**事件循环线程**上阻塞的，一个请求等连接 = 全服务停摆（解释了为什么 Redis 读会超时：响应回来了但事件循环冻结没人读）
  3. **前后台共享连接池（无舱壁）**：flusher 每 200ms 刷库事务与请求路径抢同一个 15 连接池，加剧了池压力
- **解决**：① `restore_game_state` 改用独立 `own_session` 标志记录所有权（泄漏根除）；② `get_current_user` 改同步 def（FastAPI 丢线程池执行），`create_game` 的用户名查询改为 `asyncio.to_thread` + 短生命周期 Session（连接不再跨 await 持有）；③ flusher 独立引擎 + 单连接池（前后台舱壁隔离）
- **验证（未闭合，问题仍在）**：修复后第一轮 S2 20 房间通过（创建 P50 56ms / max 290ms / 零失败），但随后干净复测一轮复现——46 次创建 13 次 500，P66+ 卡整齐的 30000ms，报错点移到 `get_current_user` 等连接。**关键证据：MySQL processlist 里所有连接 Sleep 空闲——连接是被签出后闲置持有的（僵尸请求），不是 MySQL 慢**。当前假设：`get_db` Session 从鉴权起签出、持有到请求结束，若请求卡在永不返回的 await（如 Actor `submit` 的 future 在 Actor 任务死亡后永久悬挂），连接永久泄漏，攒够 15 个池即死。下一步：开池 checkout/checkin 日志或加 pool 探针，抓"谁签出未还"（见 todo_v2 交接状态）
- **经验**：① **"P50 天文数字 + 另一部分很快"先查资源等待，别查算法**——连接池/锁/队列等待的特征就是延迟呈现"卡在超时值上"的整齐数字（90000/30000 整）；② Python 里"先赋值再判断"是资源管理经典坑——管理资源所有权要用独立标志变量，不要用被管理的对象本身做判断；③ async 框架里同步阻塞调用不会报错的特性让这类 bug 极难发现，评审 checklist 加一条："async def 里搜所有不带 await 的 IO 调用"；④ 连接池耗尽再次验证 DEVLOG 006 的传染性——这次连"看起来不相干"的 Redis 超时都是它引起的；⑤ **一轮压测通过 ≠ 修复确认**——资源泄漏类 bug 的表现随泄漏累积速度波动，至少要连续 2~3 轮干净复测才能下结论，本条目的"验证"段就是反面教材

### 009 换机环境重建：3306 被"幽灵 mysqld"劫持，验证目标身份再信数据

- **现象**：换机后重建环境，`docker-compose up -d` 报 MySQL 容器 3306 端口被占；清掉占用容器后端口能绑了，但抓 MySQL 握手 banner 发现 `127.0.0.1:3306` 应答的是 **9.7.1**（Docker 镜像是 mysql:8.0）——端口通≠目标对
- **排查**：`lsof -iTCP:3306` 发现两个监听者：Docker 代理（IPv6 `*:3306`）+ 本机 mysqld（IPv4 `127.0.0.1:3306`）；`ps` 顺藤摸瓜发现 mysqld 是另一个项目（bdata-handover）的脚本用 `mysqld_safe` 手动拉起的，`brew services stop mysql` 对它无效（不归 brew 管）
- **根因**：macOS 上 `localhost` 优先解析 IPv4 → 应用连 `localhost:3306` 会落到本机 mysqld，容器里的真身被完美劫持；不验证身份的话，应用会"成功连上错误的数据库"，表现为表不存在/认证失败等诡异报错
- **解决**：确认该 mysqld 为一次性交接任务残留后，先杀 `mysqld_safe` 父进程再杀 `mysqld`（防自动拉起）；复验 banner 变为 `8.0.46`（容器真身）
- **经验**：① **连得通 ≠ 连得对**——端口冲突排查的终点不是"端口空了"，而是"应答者身份正确"，MySQL 握手包直接带版本号，`socket.recv(64)` 就能验明正身；② 杀第三方进程先查它的启动方式（LaunchAgent / brew / 手动脚本），`mysqld_safe` 类守护进程会复活子进程，要先斩守护者；③ 换机重建的隐藏成本全在这种"上个任务的环境残留"里，重建 checklist 加一条：所有依赖端口验明 banner 身份

### 010 换机环境重建（续）：三个"起了但没完全起"的连环坑

- **现象**：重建收尾连踩三坑——① uvicorn 启动报 Redis 拒连，但 `docker exec` 里 redis-cli 正常；② 注册接口 500，日志是 instrumentator 的 `'_IncludedRouter' object has no attribute 'path'`；③ 测试 6 项 fail，报错都是 async 用例不被支持

### 005 基线发现 #2：AI 重复投票竞态（TOCTOU）

### 006 S3 压测拖死整个服务：WS 长连接独占 DB 连接池（v1 最严重缺陷）

- **现象**：S3 长连接压测，100 并发 WS 连接即 93% 失败——TCP 层 `Operation timed out`，连无 DB 依赖的 `/health` 都不响应；`sample` 采样显示事件循环空闲在 kevent，服务"活着但装死"
- **排查**：① 先怀疑 A.2 新加的 TraceIdMiddleware（BaseHTTPMiddleware 与 WS 兼容性有前科），注释后 A/B 复测——故障依旧，**中间件被排除**；② 翻 API 日志找到真凶：`sqlalchemy.exc.TimeoutError: QueuePool limit of size 5 overflow 10 reached, connection timed out, timeout 30.00`
- **根因**：三重叠加——(a) FastAPI 的 yield 依赖在 WS 端点上生命周期 = 整条连接（握手后不释放）；(b) `get_ws_user` 的 `db.query()` autobegin 事务，Session 把池连接独占整条连接 lifetime；(c) 引擎用默认池 5+10=15。于是第 16 条 WS 连接开始阻塞在池等待（30s 超时）→ 40 个线程池线程全部堵死 → 新握手无法处理 → accept 积队溢出 → 内核丢 SYN → TCP 连接超时，全服务雪崩
- **解决**：`get_ws_user` 改为手动管理短生命周期 Session（`SessionLocal()` + 用完 `close()`），握手鉴权是一次性查询，不该持有池连接
- **验证（前后对比）**：修复前 100 连接 93% 失败；修复后 100 连接 0 失败（广播 P50 6ms），1000 连接 0 失败（连接握手均值 233ms，广播 P50 46ms / P99 91ms / max 130ms）
- **经验**：① **长连接服务的资源审计要问"每连接持有成本"**——FD、内存缓冲、线程、DB 连接，任何一个被独占都会成为上限；DB 连接池是最隐蔽的一个；② 连接池耗尽的恐怖在于**传染**：耗尽的只是一个资源，死的是整个进程的所有请求（包括健康检查）；③ 排障时"事件循环空闲但 TCP 超时"这个组合指向 accept 积压，顺藤摸瓜到线程池再到连接池，层层都是排队；④ A/B 排除法要先做（中间件 10 分钟排除），避免在错误方向上深挖
