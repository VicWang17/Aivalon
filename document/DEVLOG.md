## 概念速查（面试向 · 随时补充）

> 非踩坑类：开发中遇到"不懂但必须懂"的概念，用问答式笔记沉淀在此，每条标注关联代码/配置位置。

### C01 Prometheus 是什么（2026-08-10 · A 组）

- **一句话**：专门存"监控数字"的时序数据库 + 采集器，大厂监控体系事实标准
- **核心模式是 pull**：它不是等你上报，而是每隔 15s 主动访问 `/metrics` 把当前所有数字抓走存起来（对比：MySQL 是你往里写）
- **数据结构叫时间序列**：指标名 + 一组 label = 一条随时间变化的曲线。例：`http_requests_total{handler="/health", method="GET", status="2xx"}` 就是"该接口 GET 2xx 的累计请求数"这条曲线。有了曲线就能算增速 = QPS
- **分工**：Prometheus 存数据和告警，Grafana 负责画图（Grafana 只读不存）
- **关联代码**：`backend/app/main.py` 的 `Instrumentator().expose(app)` 就是被拉的 `/metrics`

### C02 label 基数爆炸（2026-08-10 · A 组）

- **label**：指标上的维度标签，如 `{handler="/health", method="GET"}`
- **基数 = 取值个数**；**每种 label 取值组合 = 一条独立时间序列**，都要占内存
- **爆炸机制**：label 放低基数维度（路由十几个 × 方法几种 ≈ 几十条序列）没问题；放 `game_id`/`user_id` 这种高基数值，一万个房间 = 每个指标爆炸成上万条序列，Prometheus 内存打爆、查询卡死。这是 Prometheus 最经典的生产事故
- **正确分工（面试标准答案）**：metrics 看聚合趋势，日志查个案（带 trace_id/game_id），trace 看调用链——"metrics 看趋势、日志查个案、trace 看链路"
- **关联代码**：`backend/app/core/metrics.py` 头部注释；label 只用了 event_type / action_type 这类低基数维度

### C03 Histogram、桶与"P99 是估算"（2026-08-10 · A 组）

- **问题**：想算 P99 延迟，但 Prometheus 每 15s 才拉一次，拿不到每个请求的原始值，无法排序
- **Histogram 的解法**：不存原始值，只存"落在每个区间的累计个数"。区间边界就是桶（buckets）。一个延迟 37ms 的观测，会给 ≤50ms、≤100ms、≤1s……所有不小于它的桶各 +1
- **P99 怎么算出来**：总 1000 个请求，第 990 名落在哪个桶？查各桶计数找到它落在 50ms~100ms 桶，然后**假设桶内均匀分布做线性插值**，估出约 98ms——所以 P99 是估算值不是精确值
- **推论（面试追问点）**：估算精度取决于桶边界设计。桶要按"目标延迟"加密设置——我们要验证 P99 < 100ms，就在 5ms~200ms 区间密集设桶（见 `metrics.py` 的 buckets 参数）；桶设糙了 P99 就没意义
- **关联代码**：`backend/app/core/metrics.py` 的 `ws_broadcast_latency` / `game_action_latency`

### C04 Locust 是什么（2026-08-10 · B 组）

- **一句话**：用 Python 代码定义"虚拟用户行为"的压测工具——你写用户会做什么，它模拟成千上万个这样的用户并发打你的系统
- **压测工具三要素**：制造并发（N 个虚拟用户）、定义行为（节奏/接口/数据）、统计结果（QPS/分位数/错误率）
- **Locust 的差异化**：行为用 Python 类表达，`@task(权重)` 声明任务比例，`wait_time` 模拟真人思考间隔——能写多步骤有状态的行为（建房→收事件→投票），这是 wrk/ab（只能打固定 URL）做不到的
- **并发模型**：底层 gevent 协程，单进程几千并发用户（用户大部分时间在等响应，协程切换开销小）；到天花板就走 `--master`/`--worker` 多机分布式
- **选型对照**：固定接口测极限 → wrk/k6；复杂有状态行为 → Locust；GUI 拖拽老牌 → JMeter。工具服务于场景，S3 长连接场景如压不动再单补 k6
- **关联代码**：`bench/locustfile.py`（S1ApiUser 就是一个虚拟用户的定义）

## 2026-08-11 · D-2 收尾（写压力量化）

### 015 "写压力 -80%"怎么测：先想清楚"压力"是哪个维度，否则测出来是 0%

- **要回答的问题**：简历写"MySQL 写压力下降 80%"，必须有实测。但基线报告 `v1_baseline.md` **只有定性结论**（"每动作同步写 MySQL，写路径饱和"，列为 P0 瓶颈），**没有记录任何绝对写 QPS**——对照组数字根本不存在，得重新构造口径并把 v1 真跑一遍
- **先卡住一个概念陷阱**（这一步比测量本身重要）：Write-Behind **不减少落库行数**。事件该持久化的还是要持久化，只是晚 200ms。如果拿"写入行数"当指标，测出来的下降会是 **0%**——不是优化没用，是指标选错了。真正被省掉的是**事务次数**：v1 是"一个动作一个事务"，v2 是"一批事件一个事务"。每次 `commit` 都要 fsync 刷盘 + 占一个连接一个网络往返，这才是 MySQL 写路径的瓶颈所在
- **口径设计**：取 `SHOW GLOBAL STATUS` 计数器在一轮压测前后的**增量**，再**按事件数归一化**（`每事件 commit 次数`）。归一化是关键——两轮压测吞吐不同（v2 更快，同样时间打出更多事件），比绝对 QPS 会把"变快了"和"变省了"混在一起，除以事件数才是公平对比
- **对照组怎么来**：`git worktree add /tmp/aivalon_v1 a8f21ea` 检出 Write-Behind **之前**那个 commit（Actor 已有、Write-Behind 未做），从 worktree 起完整 v1 栈（API + celery + relay，共用同一 venv 与同一套中间件），跑**完全相同**的 `locust -u 10 -t 90s`。选 a8f21ea 而不是更早的 commit，是为了让两组只差 Write-Behind 这一个变量（Actor 串行化两边都有）
- **实测结果（各两轮，10 房间 × 90s）**：

  | 指标（每事件归一化） | v1 r1 | v1 r2 | v2 r1 | v2 r2 | 下降 |
  |---|---|---|---|---|---|
  | **Com_commit（事务数）** | 1.0734 | 1.0780 | **0.2036** | **0.2387** | **81.0% / 77.9%** |
  | Queries（语句总数） | 12.68 | 13.08 | 6.94 | 7.62 | 45.3% / 41.7% |
  | Handler_commit（引擎层提交） | 10.10 | 10.21 | 7.34 | 7.54 | 27.3% / 26.2% |
  | Com_insert（insert 语句数） | 2.0135 | 2.0135 | 2.0264 | 2.0276 | **-0.7%（无变化）** |
  | Innodb_rows_inserted（落库行数） | 2.0135 | 2.0135 | 2.0132 | 2.0138 | **0.0%（无变化）** |

  **结论：事务维度下降 78~81%，行数维度零下降**。v1 每事件 1.07 次 commit（一动作一事务，那 0.07 是创建对局等额外事务）；v2 每事件 0.20~0.24 次，即**平均 4~5 个事件合并进一个事务**（200ms 窗口内攒批的自然结果）。`Com_insert` 恒为 ~2.0 是因为每个事件写两行（`game_events` + `outbox_events`），两边都一样
- **副产物（同一轮数据里顺手拿到的）**：创建对局 P50 40ms → 23ms、P75 310ms → 97ms、max 380ms → 180ms；v1 有 4 次 mission 500（DEVLOG 005 竞态家族，基线里也有），v2 零失败
- **简历口径怎么写**（这条最重要）：必须写成"**MySQL 写事务数下降 ~80%**"或"写事务合并率 4~5:1"，**不能笼统写"写压力下降 80%"**——后者会被理解成写入量/行数下降，而那个数是 0%，面试官一追问"你们数据量少了 80%？"就当场崩。**量化指标的定义要跟数字一起写进简历**
- **经验**：① **优化前先问"我省掉的到底是什么资源"**——Write-Behind 省的是事务/fsync/连接往返，不是数据量。指标选错会让真实的 4~5 倍改善显示成 0%；② **对比实验要用 worktree 把对照组真跑一遍**，别信"基线报告里应该有"——本项目基线报告恰好只记了定性结论，硬凑对比就变成编数字。`git worktree` 跑历史 commit 是最干净的做法：同机、同中间件、同压测脚本，只差被测代码；③ **归一化再比较**：优化让系统变快，同样时长会处理更多请求，绝对值对比会混淆"变快"与"变省"，除以业务量（每事件/每请求）才是可比口径；④ **对照组 commit 要挑得只差一个变量**（选 a8f21ea 而非更早），否则测出来的是多个改动的叠加效果，归因不了；⑤ 两轮复测的规矩继续生效（DEVLOG 011 的教训）：v1 两轮 1.0734/1.0780、v2 两轮 0.2036/0.2387，一致性本身就是数据可信的证据
- **面试点**：① "你怎么衡量写压力下降"——标准答案是分维度：行数没降、事务数降 80%，瓶颈在事务不在行数；② "怎么保证对比公平"——同机同中间件、worktree 跑历史 commit、只差一个变量、按业务量归一化、各跑两轮；③ "省下的 80% 换来了什么代价"——RPO 从 0 变成 16 条/200ms（DEVLOG 013），这是明摆着的取舍

## 2026-08-11 · D-2 收尾（宕机恢复演练 + RPO 量化）

### 013 宕机恢复演练与 RPO 量化：Write-Behind 的丢失窗口到底有多大

- **要回答的问题**：Write-Behind 把"每动作同步写 MySQL"改成了"先写 Redis、后台每 200ms 批量刷库"，性能是买来的，代价是**引入了一个丢失窗口**。简历写"量化验证宕机恢复 RPO"就必须给出这个窗口的实测值，而不是"理论上很小"
- **先把 RPO 拆成两个维度**（这一步比测量本身重要）：
  - **时间维度**：最坏丢 ≤ 一个刷库间隔 = **~200ms**（`FLUSH_INTERVAL`），这个是设计值，看代码就知道
  - **条数维度**：已入 Redis Stream 但游标尚未推进的事件数——这才是真丢的东西，**必须实测**，因为它取决于负载
- **两类故障要分开演练**（同一个"宕机"在 Write-Behind 下有完全不同的后果）：
  1. **API 进程挂**（本次演练）：Redis 完好 → 状态快照和事件都在 → **零丢失**，对局可继续
  2. **Redis 也挂**：丢的就是上面那个"未刷条数"窗口 → 这才是 RPO 的适用场景
- **演练一：kill -9 API 进程后对局能否续打**
  - 建局打 8 个动作到 `phase=vote round=2`（27 条发言），kill 前 MySQL 57 条事件
  - `kill -9` API 进程（**注意 flusher 跑在 API 进程内，等于同时杀掉了刷库器**），健康检查 `000`，Redis 快照仍在
  - 重启后读取对局：`phase=mission round=2 speech=28`——比 kill 前更靠前一格，因为 kill 瞬间在途的动作已落 Redis
  - 续打 6 个动作到 `phase=finished round=4`，最终 MySQL 101 条事件，**distinct seq = 101，重复行 0**（`INSERT IGNORE` 幂等生效）
- **演练二：RPO 窗口实测**（`drill_kill_recovery.py watch`，20 房间负载下 45s 采样 427 次 @0.1s）

  | 指标 | 实测 |
  |---|---|
  | 峰值未刷事件数（**最坏 RPO**） | **16 条** |
  | P95 | 10 条 |
  | 均值 | 3.45 条 |
  | 非零采样占比 | 361/427（84.5%） |
  | 时间维度 RPO | ≤ ~200ms |

  即：**20 并发房间满载时，Redis 与 API 同时全灭，最多丢 16 条事件 / 200ms 窗口**。无负载时窗口恒为 0（动作节奏慢于刷库节奏，永远追平）——所以这个测量**必须在负载下做**，空跑出来的漂亮 0 是假数据
- **顺带发现**：演练的对账环节（比对 MySQL 事件数 vs max seq）挖出一个静默丢事件的 bug，见 014。**这就是做演练的额外收益——它逼你去对账，对账才会发现平时看不见的东西**
- **经验**：① **RPO 要拆维度报**——只说"200ms"是不完整的，工程上真正关心的是"这 200ms 里积压了多少条"，而这个数只能实测；② **演练要按故障域分开设计**：Write-Behind 下"API 挂"和"Redis 挂"后果完全不同，笼统说"宕机恢复"会把零丢失的场景和有损场景混为一谈；③ **flusher 与 API 同进程是个隐藏耦合**——杀 API 等于同时杀刷库器，未刷数据只能等重启后由新 flusher 从游标续刷（本次验证了续刷正确），但生产上应考虑拆独立进程；④ 演练脚本要留成可重复执行的资产（`bench/drill_kill_recovery.py` 四段式 `play/measure/resume/watch`），一次性手敲的演练等于没做——D-3 节点迁移还要再用一次
- **遗留**：`restore_game_state` 的"从 DB 重建 GameState"分支目前是 `# TODO` 返回 `None`，所以**恢复能力当前依赖 Redis 快照存在**。本次演练成立的前提是 Redis 未丢；Redis 全丢时对局无法重建（事件流在 MySQL 里，但没有回放重建逻辑）。这是 D-2 的真实边界，不含糊过去

### 014 全库 372 局零条 GAME_START：外键 + INSERT IGNORE 把"丢数据"变成了静默

- **现象**：013 的演练对账时发现一处不对——MySQL 本局事件数 101，但 `max(seq)=102`，差 1。查 seq 连续性：`min=2, max=102`，区间内**无缺口**，唯独 seq=1 不存在。而 seq=1 是固定的 `GAME_START` 事件（`game_service.py:116` 写死）。全库扫一遍：372 局对局，`GAME_START` 事件 **0 条**
- **排查**：`SHOW CREATE TABLE game_events` 看到 `CONSTRAINT game_events_ibfk_1 FOREIGN KEY (game_id) REFERENCES games (id)`。再看 `_flush_batch` 的语句顺序：**先**插事件行（`event_flusher.py:49`），**后**补建 `games` 表记录（`:77`）。GAME_START 是一局的第一条事件，它落库时 `games` 里还没有这一行 → 外键校验失败
- **根因**：`INSERT IGNORE` **把外键错误降级成 warning**——行被丢弃，语句返回成功，事务照常提交，日志一片干净。后续 seq≥2 的动作事件因为 `games` 行此时已补建好，全部正常落库，所以现象是"从 seq=2 起完整无缺口"，看起来像 seq 起始偏移而不像丢数据
- **为什么潜伏这么久**：`INSERT IGNORE` 是为"崩溃重刷幂等"引入的（游标提交后推进，崩溃会重刷 → 靠唯一约束去重）。它对 `(game_id, seq)` 唯一冲突的忽略是**故意的**，对外键失败的忽略是**顺带的副作用**——同一个关键字，一个语义想要，一个不想要，无法分开
- **解决**：把 `games` 记录的补建提到事件插入**之前**（同一事务内），依赖行先于依赖者存在。验证：新建一局，MySQL 前 3 条事件为 `(1,'GAME_START'), (2,'speak'), (3,'speak')`，seq 从 1 起；24 项测试全绿
- **经验**：① **幂等写法要审"它还忽略了什么"**——`INSERT IGNORE` 忽略的是一整类错误（唯一冲突、外键失败、类型截断……），只想要其中一种时它就是个太钝的工具。更精确的替代是 `ON DUPLICATE KEY UPDATE`（只针对键冲突）或先查后插；② **同事务内有外键依赖时，插入顺序不是风格问题而是正确性问题**——批量写路径尤其容易踩，因为语句是循环生成的，顺序藏在代码结构里而不是显式表达的；③ **静默失败比报错危险得多**：这个 bug 没有任何日志、没有异常、测试也全绿（集成测试只断言对局能打完，没断言事件完整性），只有主动对账才能发现。**"写成功"和"写进去了"是两件事**；④ **对账是发现静默 bug 的唯一手段**——顺手做的一次 `count(*)` vs `max(seq)` 比对就挖出来了，这类校验值得固化进演练脚本
- **面试点**：① "`INSERT IGNORE` 有什么坑" —— 标准答案就是这个：它忽略的错误远超你的预期；② "怎么发现数据静默丢失" —— 对账 + 不变量校验（序号连续、计数一致），不能指望报错；③ "为什么集成测试没抓住" —— 测试断言的是流程走通，不是数据完整，断言层级不同

## 2026-08-11 · D-2 收尾（30s 超时墙闭环）

### 012 30s 超时墙真凶：不是泄漏是自死锁——一个请求握着连接去要第二个连接

- **现象**：承接 011。修完三处缺陷后仍复现——20 房间 S2 压测，创建对局 66 次 13 次 500（25.76%），P75 及以后整齐卡在 30000ms（池等待超时值）；同时所有动作接口 P50 14~18ms 零失败。011 里"MySQL processlist 全是 Sleep"这条关键证据始终没被解释通
- **排查**：先做取证工具再改代码（011 的教训：假设未证实就改，一轮通过就当修好）。给连接池挂 checkout/checkin 事件监听（`app/core/pool_probe.py`），checkout 时记下 trace_id + 业务调用栈，后台每 2s 报告"持有超 5s 未还"的连接。开着探针复现，三条证据一次到手：
  1. 15 个连接**全部**签出于 `deps.py:46`（`get_current_user` 的 `db.query`），持有 5.9s 不还，池水位 `Checked out: 15 / in pool: 0` 连续 24 秒一动不动
  2. 这 15 个 trace_id 对应的请求全是 `POST /api/v1/games/`，最终 ERR 于 30.1s（池日志与访问日志靠 trace_id 串起来）
  3. 超时点分两处：**12 次**卡在 `game.py:42(_load_user_map)`、**5 次**卡在 `deps.py:46(get_current_user)`，12+5 = 17 = 全部 500 数量，账完全对上
- **根因**：**"持有并等待"自死锁**，不是连接泄漏。`create_game` 这条路径需要**两个**连接：`get_current_user` 用 `Depends(get_db)`（yield 依赖，连接持有到请求结束）拿第一个，下游 `_load_user_map` 用 `SessionLocal()` 拿第二个。20 并发下：15 个请求各抢到 1 个鉴权连接把池占满 → 它们接着都在等第二个连接 → **占着资源的正是在等资源的人**，池永不恢复 → 12 个卡在第二次获取超时；剩下 5 个连第一个都拿不到，卡在鉴权。这解释了 processlist 全 Sleep：那 15 个连接的查询早跑完了，只是被 yield 依赖握着不放
- **讽刺之处**：这个 bug 是 011 的修复引入的。011 为了"连接不跨 await 持有"，把 `create_game` 里原本复用 `db` 的用户名查询抽成独立的 `_load_user_map` + `asyncio.to_thread`——单请求持有连接数从 1 变成 2，修掉跨 await 持有却造出了双重获取
- **解决**：`get_current_user` 不再用 `Depends(get_db)`，改手动短生命周期 Session（查完立即 `close()`）——**与 DEVLOG 006 修 `get_ws_user` 完全同一招**，当时只改了 WS 路径，HTTP 鉴权路径漏了。改前查过风险：`current_user` 在全代码库只被读 `.id`（7 处），无任何 `add/refresh/delete` 回写，Session 关闭后对象 detach 不会触发 `DetachedInstanceError`
- **验证（前后对比，两轮干净复测）**：

  | 指标 | 修复前 | 修复后 r1 | 修复后 r2 |
  |---|---|---|---|
  | 创建对局失败率 | 17/66（25.76%） | **0/64** | **0/58** |
  | 创建 P50 / P75 | 32ms / **30000ms** | 21ms / 220ms | 30ms / 130ms |
  | 创建 max | 30281ms | **226ms** | **160ms** |
  | 全局吞吐 | 29.74 rps | 40.21 rps | 39.44 rps |
  | 探针 POOL LEAK | 15 次 | **0** | **0** |
  | QueuePool 超时 | 17 次 | **0** | **0** |

  两轮共 9536 个请求零失败，全局最慢请求 213ms。吞吐 +35% 是"不再堵车"的副产物
- **经验**：① **连接池的真实并发上限 = 池大小 ÷ 单请求峰值持有连接数**——池 15 不等于能撑 15 并发，这条路径持有 2 就只能撑 7 个多，20 并发必死。审计资源要按"单请求峰值持有量"算，不是按池大小看；② **区分死锁与过载**：过载是慢、压力降下来会自愈；死锁是循环等待、不会自愈。判据就是探针那张图——池水位钉在满值不动 + 持有者全部空闲（processlist Sleep），这不是"忙不过来"的样子。死锁四条件（互斥/持有并等待/不可抢占/循环等待）这里全齐，破解打"持有并等待"最有效；③ **资源类修复要重算全局资源账**：011 的改动局部完全正确（连接不再跨 await），但把单请求持有数从 1 抬到 2，全局更糟。改资源生命周期时必须问一句"改完这条路径峰值持有几个"；④ **同一个 bug 类型要全路径搜一遍**：006 已经在 WS 上修过 yield 依赖持有连接，HTTP 路径同病同因却漏了两个月。修完一处应立刻 grep 同类写法（`Depends(get_db)` 还剩谁在用）；⑤ **先取证再改代码**是这次唯一做对的流程决策——011 的假设（Actor future 悬挂导致永久泄漏）方向完全错了，Actor 全程没参与，且连接不是永久泄漏而是 30s 后随请求崩掉全部归还的周期性僵局。猜不准的时候，造工具比继续猜便宜
- **面试点**：① "池满了调大池能解决吗"——这题的标准反例，死锁下调大只是把死亡阈值从 7 并发抬到 15 并发；② "怎么判断池满是死锁还是过载"——看持有者在干什么，都在跑查询是过载，全部空闲是有人握着不放；③ "同请求内多次取连接怎么办"——复用同一 Session / 缩短前一个连接生命周期 / 拆独立池做舱壁（flusher 已用第三种）

## 2026-08-11 · D-2 收尾（S2 稳定性复测）

### 011 创建对局 90s/30s 超时墙：不是慢，是"等连接"等死的——三个叠加缺陷

- **现象**：S2 20 并发房间复测，创建对局 P50 90000ms 全部挂死、伴随 500；修复后退化版为 P75+ 卡 30s 超时墙。但已创建房间的动作处理始终很快（P50 30~40ms）——"快的很快、死的全死"是典型的**资源等待**而非**算得慢**特征
- **排查**：服务日志两类报错——`QueuePool limit of size 5 overflow 10 reached`（连接池等 30s 放弃）+ 限流器 `Timeout reading from localhost:6379`（Redis 读超时）。沿 traceback 逐层定位出三个叠加缺陷：
- **根因（三个缺陷，缺一不至于雪崩）**：
  1. **连接泄漏（真凶）**：`restore_game_state` 的 `finally` 里用 `if not db` 判断是否关闭自建 Session——但 `db` 在函数开头已被重新赋值，条件恒为假，**每次房间唤醒泄漏 1 个连接**。15 个房间唤醒即永久打满共享池（pool 5+overflow 10），此后所有请求排队 30s 等连接
  2. **事件循环冻结（放大器）**：`get_current_user`、`create_game` 是 `async def` 却直接做同步 `db.query`——等池连接是在**事件循环线程**上阻塞的，一个请求等连接 = 全服务停摆（解释了为什么 Redis 读会超时：响应回来了但事件循环冻结没人读）
  3. **前后台共享连接池（无舱壁）**：flusher 每 200ms 刷库事务与请求路径抢同一个 15 连接池，加剧了池压力
- **解决**：① `restore_game_state` 改用独立 `own_session` 标志记录所有权（泄漏根除）；② `get_current_user` 改同步 def（FastAPI 丢线程池执行），`create_game` 的用户名查询改为 `asyncio.to_thread` + 短生命周期 Session（连接不再跨 await 持有）；③ flusher 独立引擎 + 单连接池（前后台舱壁隔离）
- **验证（未闭合，问题仍在）**：修复后第一轮 S2 20 房间通过（创建 P50 56ms / max 290ms / 零失败），但随后干净复测一轮复现——46 次创建 13 次 500，P66+ 卡整齐的 30000ms，报错点移到 `get_current_user` 等连接。**关键证据：MySQL processlist 里所有连接 Sleep 空闲——连接是被签出后闲置持有的（僵尸请求），不是 MySQL 慢**。当前假设：`get_db` Session 从鉴权起签出、持有到请求结束，若请求卡在永不返回的 await（如 Actor `submit` 的 future 在 Actor 任务死亡后永久悬挂），连接永久泄漏，攒够 15 个池即死。下一步：开池 checkout/checkin 日志或加 pool 探针，抓"谁签出未还"（见 todo_v2 交接状态）
- **经验**：① **"P50 天文数字 + 另一部分很快"先查资源等待，别查算法**——连接池/锁/队列等待的特征就是延迟呈现"卡在超时值上"的整齐数字（90000/30000 整）；② Python 里"先赋值再判断"是资源管理经典坑——管理资源所有权要用独立标志变量，不要用被管理的对象本身做判断；③ async 框架里同步阻塞调用不会报错的特性让这类 bug 极难发现，评审 checklist 加一条："async def 里搜所有不带 await 的 IO 调用"；④ 连接池耗尽再次验证 DEVLOG 006 的传染性——这次连"看起来不相干"的 Redis 超时都是它引起的；⑤ **一轮压测通过 ≠ 修复确认**——资源泄漏类 bug 的表现随泄漏累积速度波动，至少要连续 2~3 轮干净复测才能下结论，本条目的"验证"段就是反面教材

### 009 换机环境重建：3306 被"幽灵 mysqld"劫持，验证目标身份再信数据

- **现象**：换机后重建环境，`docker-compose up -d` 报 MySQL 容器 3306 端口被占；清掉占用容器后端口能绑了，但抓 MySQL 握手 banner 发现 `127.0.0.1:3306` 应答的是 **9.7.1**（Docker 镜像是 mysql:8.0）——端口通≠目标对
- **排查**：`lsof -iTCP:3306` 发现两个监听者：Docker 代理（IPv6 `*:3306`）+ 本机 mysqld（IPv4 `127.0.0.1:3306`）；`ps` 顺藤摸瓜发现 mysqld 是另一个项目（bdata-handover）的脚本用 `mysqld_safe` 手动拉起的，`brew services stop mysql` 对它无效（不归 brew 管）
- **根因**：macOS 上 `localhost` 优先解析 IPv4 → 应用连 `localhost:3306` 会落到本机 mysqld，容器里的真身被完美劫持；不验证身份的话，应用会"成功连上错误的数据库"，表现为表不存在/认证失败等诡异报错
- **解决**：确认该 mysqld 为一次性交接任务残留后，先杀 `mysqld_safe` 父进程再杀 `mysqld`（防自动拉起）；复验 banner 变为 `8.0.46`（容器真身）
- **经验**：① **连得通 ≠ 连得对**——端口冲突排查的终点不是"端口空了"，而是"应答者身份正确"，MySQL 握手包直接带版本号，`socket.recv(64)` 就能验明正身；② 杀第三方进程先查它的启动方式（LaunchAgent / brew / 手动脚本），`mysqld_safe` 类守护进程会复活子进程，要先斩守护者；③ 换机重建的隐藏成本全在这种"上个任务的环境残留"里，重建 checklist 加一条：所有依赖端口验明 banner 身份

### 010 换机环境重建（续）：三个"起了但没完全起"的连环坑

- **现象**：重建收尾连踩三坑——① uvicorn 启动报 Redis 拒连，但 `docker exec` 里 redis-cli 正常；② 注册接口 500，日志是 instrumentator 的 `'_IncludedRouter' object has no attribute 'path'`；③ 测试 6 项 fail，报错都是 async 用例不被支持

### 005 基线发现 #2：AI 重复投票竞态（TOCTOU）

- **现象**：S2 冒烟中 worker 日志反复出现 `API Error 400: 您已经投过票了`——同一个 AI 被重复调度投票任务，第二次提交被拒绝

- **经验**：① 压测的价值复证：这个竞态在低并发下几乎不触发，只有并发房间+并行 AI 调度才暴露；② "检查再行动"跨进程必然有窗口，解法要么串行化（Actor）、要么乐观重试（当前服务端 400 拒绝事实上就是兜底）

### 006 S3 压测拖死整个服务：WS 长连接独占 DB 连接池（v1 最严重缺陷）

- **现象**：S3 长连接压测，100 并发 WS 连接即 93% 失败——TCP 层 `Operation timed out`，连无 DB 依赖的 `/health` 都不响应；`sample` 采样显示事件循环空闲在 kevent，服务"活着但装死"
- **排查**：① 先怀疑 A.2 新加的 TraceIdMiddleware（BaseHTTPMiddleware 与 WS 兼容性有前科），注释后 A/B 复测——故障依旧，**中间件被排除**；② 翻 API 日志找到真凶：`sqlalchemy.exc.TimeoutError: QueuePool limit of size 5 overflow 10 reached, connection timed out, timeout 30.00`
- **根因**：三重叠加——(a) FastAPI 的 yield 依赖在 WS 端点上生命周期 = 整条连接（握手后不释放）；(b) `get_ws_user` 的 `db.query()` autobegin 事务，Session 把池连接独占整条连接 lifetime；(c) 引擎用默认池 5+10=15。于是第 16 条 WS 连接开始阻塞在池等待（30s 超时）→ 40 个线程池线程全部堵死 → 新握手无法处理 → accept 积队溢出 → 内核丢 SYN → TCP 连接超时，全服务雪崩
- **解决**：`get_ws_user` 改为手动管理短生命周期 Session（`SessionLocal()` + 用完 `close()`），握手鉴权是一次性查询，不该持有池连接
- **验证（前后对比）**：修复前 100 连接 93% 失败；修复后 100 连接 0 失败（广播 P50 6ms），1000 连接 0 失败（连接握手均值 233ms，广播 P50 46ms / P99 91ms / max 130ms）
- **经验**：① **长连接服务的资源审计要问"每连接持有成本"**——FD、内存缓冲、线程、DB 连接，任何一个被独占都会成为上限；DB 连接池是最隐蔽的一个；② 连接池耗尽的恐怖在于**传染**：耗尽的只是一个资源，死的是整个进程的所有请求（包括健康检查）；③ 排障时"事件循环空闲但 TCP 超时"这个组合指向 accept 积压，顺藤摸瓜到线程池再到连接池，层层都是排队；④ A/B 排除法要先做（中间件 10 分钟排除），避免在错误方向上深挖

### 002 prometheus-fastapi-instrumentator 8.x 与 fastapi 的 starlette 版本冲突

- **现象**：接入指标库后 uvicorn 启动即崩，`TypeError: Router.__init__() got an unexpected keyword argument 'on_startup'`，报错栈在 `app/routers/auth.py` 的 `APIRouter()`——看上去像是自己代码的问题
- **排查**：`pip check` 一把出真相：`fastapi 0.128.0 has requirement starlette<0.51.0,>=0.40.0, but you have starlette 1.6.0`；查 instrumentator 的依赖约束发现 8.x 强制 `starlette>=1.0.0,<2.0.0`——pip 装它时把 starlette 从 0.40.x 升到了 1.6.0，fastapi 被拖垮
- **根因**：两个依赖对 starlette 大版本的要求互斥（fastapi 0.128 锁 <0.51，instrumentator 8.x 锁 >=1.0），pip 按后装的包解析，破坏了先装的
- **解决**：instrumentator 降到 `7.1.0`（兼容 starlette 0.x），starlette 回落 0.50.0，`pip check` 转绿；requirements.txt 加 `<8.0.0` 上限并注释原因
- **经验**：① **装新依赖后先 `pip check` 再启动**，比看报错栈快得多——报错栈指到的往往是受害者不是肇事者；② 依赖冲突在排障中的优先级要前置：功能没动过却起不来，先怀疑环境/版本，再怀疑代码；③ requirements 里发现过的冲突要留上限约束 + 注释，否则下次有人 `pip install -U` 又踩一遍
