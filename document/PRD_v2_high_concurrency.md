# PRD v2｜Aivalon 高并发架构升级

> 版本：v2.0（架构升级专项）
> 前置文档：`document/PRD.md`（产品功能 PRD，本文档不改变产品玩法，只升级技术架构）
> 定位：面向大厂后端架构面试的高并发实战项目，同时是一个真实可压测、可演练的分布式实时游戏系统。

## 1. 背景与目标

### 1.1 背景
- Aivalon v1 已完成完整产品闭环：账号、对局状态机、WebSocket 实时对局、事件溯源落库、LLM 驱动 AI、Redis 热榜、Outbox + 幂等 + DLQ 可靠性链路。
- v1 架构为单体式：API / WS / 状态机 / 广播同进程，每个动作同步写 MySQL，无业务缓存，无压测数据，无可观测性。
- v2 目标是把项目升级为**高并发实时系统的架构样本**：能讲清每个决策的瓶颈、取舍与数据，所有优化均有压测报告与故障演练记录背书。

### 1.2 目标陈述（重要）
- "亿级流量"是设计视野，不是验收指标。**可验证目标为：万级并发房间、十万级 QPS、万级长连接**，全部有压测报告。
- 坚持"深度 > 广度"：四条主线做深做透，拒绝无数据背书的组件堆砌。
- 每个架构决策沉淀一篇 ADR（架构决策记录），形成可面试复用的叙事资产。

### 1.3 成功指标（验收标准）

| 类别 | 指标 | 目标值 | 验证方式 |
|---|---|---|---|
| 性能 | 单机对局动作处理 | ≥ 5,000 TPS，P99 ≤ 50ms | 压测报告（优化前后对比） |
| 性能 | 单房间操作延迟（action→广播送达） | P99 ≤ 100ms | 链路打点 + 压测 |
| 性能 | 排行榜接口 | P95 ≤ 10ms，可承受 10,000 QPS 读 | 压测报告 |
| 规模 | 单节点长连接 | ≥ 20,000（Python 网关）/ ≥ 100,000（如引入 Go 网关） | 连接压测 |
| 规模 | 集群并发房间 | ≥ 10,000 房间同时活跃 | 集群压测 |
| 韧性 | Redis 整体宕机 | 核心对局链路自动降级，不雪崩 | 故障演练记录 |
| 韧性 | Celery worker / MQ 宕机 | 对局可继续（规则 AI 兜底），恢复后无重复结算 | 故障演练记录 |
| 韧性 | 热 key 失效瞬间 | 回源请求 ≤ 1 个（singleflight 生效） | 演练 + 监控截图 |
| 交付 | ADR 文档 | ≥ 8 篇，每篇含瓶颈数据 / 候选方案 / 取舍 / 验证结果 | 文档评审 |
| 交付 | 压测基线与对比报告 | 每个里程碑一份 | 报告归档 |

### 1.4 范围边界
**In Scope（实现 + 验证）**：热路径重构、广播优化、缓存体系、排行榜重构、限流降级熔断、可观测性、压测体系、故障演练。
**Design Only（只出设计文档与小规模 demo，不全面实现）**：分库分表、单元化、异地多活、Go 版 WS 网关。
**Out of Scope**：产品新玩法、匹配大厅、多人联机对局（真人 vs 真人）、移动端。

## 2. 现状瓶颈分析（升级依据）

| # | 瓶颈 | 现状 | 后果 | 对应主线 |
|---|---|---|---|---|
| B1 | WS 连接管理 | 单进程内存 `socket_manager`，广播 O(N) 遍历 | 无法多机部署，连接数天花板 ~1 万 | M2 |
| B2 | 对局写路径 | 每个 action 同步写 MySQL（行锁 + insert） | 单机数百 TPS 封顶，DB 先死 | M1 |
| B3 | AI 决策链路 | LLM 秒级延迟，Celery `prefetch=1` 易积压 | 突发时 AI 队列堆积，全房间卡住 | M1/M4 |
| B4 | 排行榜 | 单 ZSET 热 key，无本地缓存 | 热 key 打满、赛季切换空窗 | M3 |
| B5 | 业务缓存 | 快照/历史/回放直读 MySQL，缓存体系空白 | DB 读压力大，无抗突发能力 | M3 |
| B6 | 韧性体系 | 有 Outbox/幂等/DLQ 但无演练证据；无限流降级矩阵 | 机制有效性未证明 | M4 |
| B7 | 可观测性 | 无指标、无链路打点、无结构化日志 | 无法压测定位瓶颈（阻塞一切优化） | M0 |

## 3. 主线需求详述

### M0｜可观测性与压测基线（最高优先级，其他主线的前置）

**R-M0-1 指标体系**
- 接入 Prometheus + Grafana，覆盖：API QPS/延迟分位数、WS 连接数、活跃房间数、事件写入速率、AI 队列积压深度、LLM 调用耗时/失败率、Redis/MySQL 耗时、广播延迟。
- 结构化日志：请求级 trace_id，串联 game_id / user_id / event seq。

**R-M0-2 压测平台**
- 选型：Locust 或 k6（需支持 WS 长连接场景）。
- 标准场景集：
  - S1 纯 API：注册/登录/历史/热榜读接口梯度加压；
  - S2 对局主链路：N 并发房间全自动对局（规则 AI），测量 action 吞吐与延迟；
  - S3 长连接：梯度建立 WS 连接，测单节点上限与广播延迟分布；
  - S4 突发流量：1 分钟内 10 倍流量冲击，观察限流/降级行为；
  - S5 热点场景：单房间大量旁观连接 + 热榜集中读。
- 产出：v1 基线报告（每项指标的当前值与第一瓶颈定位），作为后续所有优化的对照组。

**验收**：基线报告归档至 `document/benchmark/v1_baseline.md`；Grafana 面板可实时观察压测过程。

### M1｜对局热路径重构（核心主线）

**目标**：将 MySQL 摘出对局主链路，单房间操作 P99 ≤ 100ms，单机对局动作 ≥ 5,000 TPS。

**R-M1-1 房间 Actor 内存状态机**
- 每个活跃房间由一个 Actor 独占推进（单写者），动作串行化，消除分布式锁开销。
- 房间 → 节点路由：一致性哈希（带虚拟节点），路由表存 Redis，支持节点上下线迁移。
- Actor 休眠与唤醒：无活动房间超时卸载状态，新动作触发从 Redis/DB 重建。

**R-M1-2 写路径异步化（Write-Behind）**
- 事件写入路径：Actor 内存 → Redis Stream（持久化兜底，双写）→ 异步批量刷 MySQL。
- 批刷策略：按时间窗口（如 200ms）或批量大小（如 100 条）触发，单调 seq 保证不乱序。
- 宕机恢复：节点崩溃后由 Redis Stream 中未刷盘事件 + 定期 snapshot 重建房间状态，量化 RPO 并写入 ADR。
- Outbox 模式保留，角色从"主链路可靠性"调整为"持久化与下游分发兜底"。

**R-M1-3 AI 链路改造**
- AI 决策抽象为接口：`RuleEngine`（默认，微秒级）/ `LLMEngine`（增强，可整体摘除）。
- LLM 调用增加独立线程/连接池与舱壁隔离，超时/失败自动回落规则引擎。
- AI 发言降级为可选增强项，挂载降级开关（见 M4）。

**关键取舍（须写入 ADR）**：内存态 vs 一致性、RPO 窗口的选择、Redis 双写的成本。

**验收**：S2 场景压测达标；kill 房间节点后房间自动迁移且事件不丢不重；MySQL 写入 QPS 较基线下降 ≥ 80%。

---

### M2｜长连接与广播优化（差异化主线）

**目标**：单节点 ≥ 20,000 WS 连接，广播 P99 延迟 ≤ 200ms，支持多网关节点水平扩展。

**R-M2-1 接入层与逻辑层分离**
- WS 网关服务独立部署，只负责：连接维持、鉴权（握手 token 校验）、消息收发转发。
- 连接 → 网关节点映射存 Redis；逻辑层广播时按房间查询映射，跨节点扇出经消息通道（Redis Pub/Sub 或 MQ topic）。
- 客户端协议保持兼容：断线重连仍走"HTTP 快照 + WS 增量"，补充增量事件的幂等去重（按 seq）。

**R-M2-2 广播优化（骚操作集）**
- 事件合并：同房间同 Tick 内多个事件合并为一帧推送（如一轮投票 8 个事件合并）；
- 分级推送：操作者即时单播、同房间即时广播、旁观者聚合批量推送（可配延迟窗口）；
- 背压保护：慢消费者（写缓冲区超阈值）主动断开，避免拖垮节点内存；
- 广播限频：单房间每秒推送帧数上限，防事件风暴。

**R-M2-3（Design Only + Demo）Go 接入层**
- 产出设计文档：为什么 Python 不适合百万级长连接网关（GIL、内存占用、每连接成本对比数据）。
- 可选 demo：Go 实现的极简网关（连接转发 + 订阅），压测对比单节点连接数。

**验收**：S3 场景压测达标；网关节点从 1 扩到 3，广播延迟不劣化；慢消费者被隔离不拖垮节点。

### M3｜缓存体系与排行榜（经典题主线）

**目标**：排行榜读 P95 ≤ 10ms @ 10,000 QPS；缓存三兄弟各有真实落地场景与演练记录。

**R-M3-1 多级缓存体系**
- L1 进程内缓存（对局快照、热榜 Top N、persona 配置，秒级 TTL）+ L2 Redis + L3 MySQL。
- 失效策略：对局快照采用事件驱动失效（事件推进时主动失效）+ TTL 兜底。

**R-M3-2 缓存三大经典问题实战**
- 穿透：布隆过滤器拦截不存在的 game_id/user_id（回放、历史接口）；空值短 TTL 缓存兜底。
- 击穿：热点 key（进行中对局快照）singleflight 互斥回源——同一时刻仅一个请求查库，其余等待/返回旧值。
- 雪崩：TTL 随机抖动（基础）+ 热点数据逻辑过期（value 内嵌过期时间，到期异步重建，物理不过期）。

**R-M3-3 排行榜重构**
- 写：对局结束 → MQ → 批量合并 ZINCRBY（合并窗口内同玩家多次变更）。
- 读：分片 ZSET（按分数段分片）+ 定时归并 Top N 至独立热 key + L1 本地缓存（1~3s）。
- 赛季切换：新赛季 key 预建预热，旧赛季归档快照表，原子切换避免空窗期。

**R-M3-4 缓存预热**
- 服务启动预热：persona、规则配置、活跃房间快照、热榜 Top N；
- 发布流程：新实例预热完成 → 就绪探针通过 → 才接入流量；
- 赛季重置、大规模失效前主动预建。

**验收**：S5 场景压测达标；演练记录三份——(a) 刷不存在 game_id 时 DB 零查询；(b) 热 key 失效瞬间回源请求 = 1；(c) Redis 全量重启后系统无雪崩（限流 + 降级生效）。

### M4｜韧性工程：限流、降级、熔断与演练（拔高主线）

**目标**：任意单一依赖（Redis / MQ / Celery / LLM / MySQL 慢查询）故障时，核心对局链路不中断或可预期降级，全部有演练证据。

**R-M4-1 限流体系（分层）**
- 网关层：全局限额（令牌桶）+ IP 维度限流；
- 应用层：用户级滑动窗口（登录、创建对局、动作提交，延续 v1 实现并补齐场景）；
- 资源层：单房间事件风暴保护、AI 队列深度上限 + 拒绝策略。

**R-M4-2 降级矩阵（预定义、可灰度、可一键触发）**

| 级别 | 触发条件 | 动作 | 保住什么 |
|---|---|---|---|
| L1 | AI 队列积压 > 阈值 | 关闭 AI 发言 | 对局流程 |
| L2 | LLM 失败率 > 阈值 | AI 全部切规则引擎 | 对局节奏 |
| L3 | 系统负载 > 阈值 | 回放/历史查询延迟容忍，热榜降频更新 | 写路径 |
| L4 | 接近容量 | 创建对局排队（异步通知开局） | 已有对局 |
| L5 | 过载 | 拒绝新开对局，只服务进行中房间 | 核心状态机 |

**R-M4-3 熔断与可靠性补强**
- 依赖调用全部带熔断器（LLM、统计服务、邮件等），熔断自动挂载降级。
- 修复 v1 遗留：Outbox relay 失败事件当前直接标 failed 不重试 → 指数退避重试（≤ 5 次）→ DLQ → 告警。

**R-M4-4 故障演练（Chaos Lite）**
- 标准演练清单：kill Celery worker、停 RabbitMQ、Redis 宕机、MySQL 注入 2s 慢查询、网关节点宕机、AI 队列灌入 10 倍任务。
- 每次演练产出记录：故障注入方式 → 系统表现（监控截图）→ 是否符合预期 → 修复项。

**验收**：6 项演练全部通过且有记录；S4 突发流量场景下降级矩阵按预期逐级触发。

### M5｜叙事资产（贯穿全程）

- **R-M5-1 ADR**：每个重大决策一篇，存放 `document/adr/`，模板固定：背景与瓶颈（含数据）→ 候选方案对比 → 决策与取舍 → 验证结果。必写清单：
  1. 房间 Actor 单写者 vs 分布式锁
  2. Write-Behind 的 RPO 取舍
  3. Redis Stream vs 直接 MySQL 批量写
  4. WS 网关分离与 Python/Go 选型
  5. 广播合并与分级推送
  6. 排行榜分片与归并方案
  7. 逻辑过期 vs 物理过期
  8. 降级矩阵设计
- **R-M5-2 README 演进叙事**：v1 → v2 架构演进图，每阶段标注瓶颈、优化手段、前后数字对比。
- **R-M5-3 压测报告归档**：`document/benchmark/`，每里程碑一份，含环境、工具、参数、结果、结论。
- **R-M5-4 Design Only 文档**：分库分表方案、单元化与多活演进方向（标注"设计验证级别"）。

## 5. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 单机上无法模拟"万级房间"所需资源 | 验收数字打折 | 提前测单房间资源占用，换算容量模型；必要时用多容器模拟集群 |
| 重构破坏 v1 已有功能（对局正确性） | 项目倒退 | 先补状态机单测与 API 集成测试（v1 欠债），重构期间测试常驻 CI |
| LLM 成本/稳定性干扰压测 | 数据噪声 | 压测统一走规则 AI；LLM 路径单独小流量验证 |
| 范围蔓延（想做的太多） | 烂尾 | 严守四条主线；Design Only 项只写文档不实现 |
| 过度设计（无瓶颈驱动的组件引入） | 面试减分 | 每引入一个组件必须先有基线数据证明瓶颈存在 |

## 6. 技术选型变更（相对 v1）

| 领域 | v1 | v2 | 理由 |
|---|---|---|---|
| 对局状态 | MySQL 同步写 | 内存 Actor + Redis Stream + 批量落库 | B2：DB 写放大是首要瓶颈 |
| WS 层 | FastAPI 内置 | 独立网关服务（Python 起步，Go 为演进选项） | B1：连接与逻辑解耦，独立扩缩容 |
| 跨节点广播 | 无（单进程） | Redis Pub/Sub 或 MQ topic 扇出 | B1：多网关节点必需 |
| 缓存 | 仅 Redis（限流/幂等） | L1 本地 + L2 Redis 多级缓存 + 布隆过滤器 | B4/B5 |
| 消息队列 | RabbitMQ | 保留；高吞吐事件流场景评估 Kafka（需先有压测数据支撑再引入） | 不为换而换 |
| 可观测 | 无 | Prometheus + Grafana + 结构化日志 | B7 |
| 压测 | 无 | Locust/k6 + 标准场景集 | B7 |
| AI | LLM 全量驱动 | 规则引擎默认 + LLM 可降级增强 | B3：成本与延迟在规模化下不可行 |
